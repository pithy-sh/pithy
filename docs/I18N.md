# Language

Pithy has one translator seam and every user-facing string goes through it. `c.var.t` is on every request whether or not you compose anything, because core seeds it with the English each composed capability contributed; `@pithy-sh/i18n` replaces that translator with one that negotiated the reader's locale and merged the catalogs behind it. A project that never composes the capability is byte-identical to one from before any of this landed.

This is the rule, stated once, for adopters. Every other doc links here rather than restating it.

## The interface

One object, on the request as `c.var.t` and in a React tree through `useTranslator`:

```ts
t.t(key, params?)                       // "auth/sign_in.title" → "Welcome."; the KEY itself on a miss
t.maybe(key, params?)                   // the same lookup, but `null` on a miss — see Errors, below
t.plural(key, count, params?)           // looks up `<key>.<category>`, falls back to `<key>.other`
t.formatNumber(value, options?)
t.formatCurrency(value, currency, options?)
t.formatDate(Date | number, options?)
t.formatList(values, options?)
t.formatRelativeTime(value, unit, options?)
t.catalogLocale                         // the locale whose words answered
t.formattingLocale                      // the locale handed to Intl
t.direction                             // "ltr" | "rtl"
```

`c.var.locale` carries the same three facts as a `LocaleContext` and is `null` unless the capability is composed — which is what "nothing was negotiated" looks like, as distinct from "the default was chosen". Read `t` to render a string; read `locale` when you need the tags themselves, for `lang`/`dir` on a document or the locale stamped onto an email job.

**The two locales are two facts, and collapsing them is a bug.** `catalogLocale` falls back: an `es-AR` reader reads the `es` catalog, because `es` is what somebody wrote. `formattingLocale` does not: that reader gets `es-AR` handed to `Intl`, which supports it natively whether or not a translator ever did. So Buenos Aires gets Spanish sentences and Argentine dates with nobody writing an `es-AR` catalog.

## Where a person's locale lives

**`pithy_auth_users.locale` is the one home for a person's language.** It is nullable, and null means *this reader has never chosen* — not `en`. That distinction is the column's whole purpose: null falls through to `Accept-Language`, and `en` asserts a choice nobody made.

A reader writes it through Better Auth's own `updateUser({ locale })`. It is the one kit field on the user table declared `input: true`, guarded by the same `Locale` schema that guards every read, and it accepts `null` so a reader can take a choice back.

**Do not put language in your own preferences table.** A preferences table is the right home for display formatting — time zone, date format, a 24-hour clock — and none of that is language. Two homes for one fact is not a duplicate row, it is a magic-link email in the wrong language with nothing anywhere failing to say so: the send Workflow reads the auth column, your settings pane reads yours, and the two disagree silently and permanently. Store the tag on the account, and let your preferences table hold the things that genuinely are not it.

That is also why the browser chain puts `account` above `storage`. A reader who picks Spanish on their phone must not be reading French on their laptop because that laptop's `localStorage` holds an older choice. `?lang=` still outranks both — it is this page, right now — and the way to keep it from becoming a second home is to write a signed-in reader's choice through to their account, not only to the device. `useNegotiatedLocale` takes a `persist` callback for exactly that and calls it whenever a reader picks a language. It is a seam rather than something the kit does for you because the write goes through Better Auth's own `updateUser`, which `@pithy-sh/i18n` never imports — pass it whenever a reader is signed in, or the ordering above describes a value nothing updates.

## Catalog keys

A key is `<domain>/<path>`.

`<domain>` is a capability's `name` — the same segment that is already the `pithy add` argument, the migration namespace, the `pithy_<name>_*` table prefix and the error-code domain. `<path>` is that capability's own name for the string, lower-case, `_` inside a word and `.` between levels: `auth/sign_in.title`, `email/magic_link.expiry.one`, `payments/pricing.buy.label`. A tag is at most 64 characters and a key at most 129.

**A capability may only declare keys under its own name, and `composeMessages` throws otherwise.** This is the table-prefix rule and the error-code rule for the third time, for the same reason: the domain segment is what makes two capabilities' contributions incapable of colliding, so merge order stops being something anyone has to reason about.

**A kit sentence lives in one place, and which package that is follows how it reaches a reader.** `@pithy-sh/i18n` holds what no capability can: the error taxonomy, whose domains are not capability names, and the screens, which are copied into your repository rather than imported. A capability holds its own domain in every language it is written in — `@pithy-sh/email` carries its `email/` translations beside its English, because the send Worker is a separate deploy that has to be built with them. Either way it ships in a package and reaches you as an upgrade; neither is ever copied into your tree.

**Your catalogs go under your own domain, contributed by your `app` capability like any other.** `board/nav.settings` is yours to declare. `auth/sign_in.title` is not — but *overriding* it is always allowed, and that is a different act:

- **Overriding a kit key** is one entry in `i18n({ messages })`. Always allowed, in any locale, for any key the kit ships.
- **Declaring a new key under a kit domain** through `Capability.messages` is refused, with the offending key and the domain named.

The layers `t(key)` walks, **per key**: your catalog for the resolved locale, your catalog for the project default, the kit's translation for the resolved locale, every composed capability's English for the resolved locale, then that English for the project default. Per key, never per catalog — so overriding one sentence is one entry and every key you did not mention keeps flowing from the package. That is what makes an override a merge rather than a fork.

## Errors carry a code and params, never a translated message

`ErrorPayload.message` is English, permanently, and the server never translates it. It is two things at once — the operator's diagnostic in the log line and the audit row, and the fallback for every client that cannot do better — and a server that translated it would lose the first to gain the second, for a caller whose locale it may not even have.

So the payload carries an optional `params` beside `message`, and a translating client renders:

```ts
t.maybe(payload.code, payload.params) ?? payload.message;
```

**`maybe`, not `t`.** `t` is total — a screen always has to render something, so a key nobody has comes back as the key itself. That makes it useless as a signal here, and `t(code) ?? message` never falls back: `??` sees a string and takes it, so a caller in a locale your catalog does not cover reads `auth/invalid_token` on their screen instead of the English sentence the server took care to send. `maybe` answers `null` on a miss, which is what the `??` is for.

**For an error the key *is* the code.** `auth/invalid_token` is a catalog key and an error code and the same string. There is no second identifier to keep in sync, and `KitErrorCode` is the exact checklist a locale has to cover.

**So model a failure as `code` + `params`, not as a message alone.** A message with the value baked into the sentence — `"That board does not exist: weekly."` — is one string a client can only print. The same failure as `code: "leaderboard/board_not_found"` with `params: { board: "weekly" }` is a sentence any client can rewrite in any language, and the English still arrives on the wire for the ones that do not. Every throw-sugar constructor in the kit accepts `params`, and a repo-wide gate keeps it that way.

## The catalogs live in the package, and the screens do not

The kit's translations are **never copied into your repository**. If the Spanish for `auth/sign_in.title` lived in your tree, a typo fix or a new locale could never reach you, and every adopter would be a fork on the day they scaffolded. Passing a whole locale object to `messages` **is** the fork, which is why no eject command is offered for this and none is needed.

Screens are the opposite, and the difference matters more than it looks. `pithy ui add` writes a file **once** and from that moment the file is yours — see [`docs/UI.md`](UI.md) § *Ownership*. Each screen it writes carries its own English in a `satisfies MessageCatalog` block, because that block is the catalog that survives being copied.

**There is no update path that pushes new `t` calls into screens you already have.** Pithy never rewrites a file it has written. A later release adding a sentence to the kit's sign-in screen changes the template in `@pithy-sh/ui-react`, not the copy in your repository. What upgrades on its own is everything on the other side of the seam: the negotiation, the merge order, the kit's translations, the formatting. The screen is what you consume it with.

The same is true of `client-env.d.ts`. It is generated in the kit from each capability's declared client projection and **copied** by `pithy ui add`, so an existing project's copy is hand-maintained: the `declare module "virtual:pithy/i18n"` block will not arrive on its own. Add it by hand, or scaffold a throwaway Worker with `pithy ui add` and copy the block across. Until you do, `import i18n from "virtual:pithy/i18n"` is an unresolved module to your compiler and serves correctly at runtime — the plugin builds the module from your composed config either way.

## Email: the shell follows the job, the payload is yours

An email is rendered twice in two places: the subject at enqueue, inside a request that knows the reader, and the body at send, inside a Workflow with no request on it at all. So the locale is stored on the job row, and `null` there means the same thing it means on the user row — nobody chose, render the kit's English.

**The rendered subject comes back on the enqueue result, so nobody renders it twice.** A surface with an administrative trail has to record what it queued, and `EnqueueResult.subject` is the sentence the job row was written with. Rendering it again to write it down means restating the theme and the layer stack, and a trail that mirrors the kit's English by hand instead of rendering agrees with the row only until a locale is passed — at which point the template renders the reader's catalog and the mirror keeps restating English. It is the **enqueue-time** render, though: `runSend` renders once more at the moment the message leaves and rewrites the column from that, so a scheduled job whose catalog was retranslated in between delivers the new sentence while the recorded value keeps the old one.

Seven templates are the kit's own copy and are translated with it: `magicLink`, `otp`, `welcome`, `securityAlert`, `invite`, `passwordChanged`, `leadCapture`. Five are not, because their words arrive as payload: `testerNudge`, `supportReply`, `operationalNotice`, `newsletter`, `marketingCampaign`.

**The shell follows the job's locale; a payload-carrying template is only as localized as your own copy.** Concretely: an `operationalNotice` enqueued at locale `es` builds its subject as `{severity label}: {summary}`, takes the label from the Spanish catalog (`email/severity.info` is `Aviso`) and the summary straight from your payload, and delivers `Aviso: A signing key did not roll`. That is correct behavior — the half the kit wrote is translated and the half you wrote is not — and it is a surprise unless somebody says it out loud.

The answer is to localize your own copy, through your own domain catalog, before you enqueue. Look the summary up with `c.var.t.t("app/key_rotation.failed", { key })` — a key under your own capability's name, translated in your own `messages` — and hand the rendered string to `enqueueEmail` along with the same `locale`. The kit cannot do this for you: a catalog cannot translate a sentence it has never seen.

### How the words reach the send Worker

The send Workflow runs in its own Worker, deployed by `pithy email provision` and by `pithy testers provision`. It has no request and no access to your `pithy.config.ts`, so anything it does not carry in its own bundle has to be stamped into it as configuration.

**It is built with the kit's own email copy, in every language the kit is written in.** Adding a locale the kit ships therefore costs you a package upgrade and no configuration at all. What still travels is your diff against it: the `email/` sentences you changed, one variable per locale, and nothing if you changed none.

That matters because a Cloudflare Worker variable holds 5120 bytes. Held as configuration, the kit's own Spanish filled 61% of one on its own — static data crossing a config channel on every provision run. Held in the bundle, the ceiling stops being reachable by anything the kit ships, and what remains is a guard on a single override set outgrowing a variable: provisioning refuses that, naming the language and the byte count rather than truncating, because a shortened catalog is a letter half in Spanish and half in English with nothing failing to say so.

Nothing else is bounded this way. Screens are negotiated in the browser and fetched one locale at a time as their own chunk; errors carry their English on the wire and are translated by the client from a catalog it already holds.

**No catalog value may carry markup.** `subject` and the plain-text part are precompiled with escaping off, so a value substituted there is substituted verbatim. The HTML body escapes what it renders, and interpolated parameters are escaped with the sentence that carries them.

## Writing a locale

Add the tag to `supportedLocales`, then add keys under it in `messages`. Ship the least specific tag that is true — `es`, not `es-ES` — because the catalog locale falls back and the formatting locale does not, so a regional reader already gets regional dates from a plain `es` catalog.

**A catalog file written in a language other than English declares itself in its head.** This repository's American-English census reads all committed prose, and a Spanish catalog is prose that is *supposed* not to be American English. A path list would answer that and is exactly what a census must not grow, so the file says what it is instead — within its first 25 lines, exactly this:

```
// LOCALE es — an unreviewed first pass. Not American English by design.
```

Two facts in one line, and both are load-bearing. The **locale** it is written in, and that the copy is an **unreviewed first pass** — which is the honest state of the kit's own `es` today. A census that reads the tag still reads a file declaring `en`, so the marker cannot become a way to opt English prose out of the rule.

**It exempts the file's quoted values, not the file.** A catalog is not written in Spanish — its *values* are. Everything around them is a docblock, an import and an identifier: this project's own English prose, and exactly as subject to the rule as any other file's. So inside a file carrying the marker every quoted run counts as a value, whole sentences included, rather than only the whitespace-free tokens the census exempts everywhere else — and every line outside the quotes is read exactly as it would be in any other file. A run is one line's worth: the census reads line by line and a quote that never closes on its line opens no value, so the inner lines of a multi-line template literal are read as prose. Skipping the whole file instead made the kit's own `es/errors.ts` a place where a twenty-seven-line English argument went unread, which is a gate that cannot fail on most of what it is looking at.

The spelling is published here rather than kept private to the test, so that a project running its own prose census can teach it ours instead of inventing a second one. It is pinned: `packages/cli/src/ci/americanEnglish.test.ts` reads the line out of this document, holds it to the pattern the census matches, and fails if the two ever say different things.

## What stays English, on purpose

**Every operator surface.** CLI output, `renderTerminal`'s problem and action lines, `--json` lines, logs, audit rows. They stay English permanently so they stay greppable and keep matching the documentation, and because `action` is the operator's field by definition — it names `pithy` commands, repository files and wrangler bindings, none of which translate. A remedy a *caller* needs is a `message`, not an `action`.

**Zod's field-level `issues[]`, in v1.** A `validation/invalid_input` payload's `message` translates like any other code, but the per-field issue messages inside it — `Invalid input: expected number, received string` — do not.

This is a reachability problem, not a Zod one. Zod 4.4.3 has exactly the right primitive: a per-parse error map, `safeParse(data, { error: z.locales.es().localeError })`, which is request-scoped and outranks both global `z.config` slots. What it cannot be reached through is the kit's actual validation surface. Every route declares its request contract with `zValidator` from `@hono/zod-validator@0.9.0`, which calls `schema.safeParseAsync(value)` with no third argument; its `validationFunction` escape hatch receives `(schema, value)` and never the Hono `Context`, and is constructed at route-definition time rather than per request. Getting a request's locale into that call needs `AsyncLocalStorage`, which is out of scope for v1.

The global slot is not the workaround, and it is banned repo-wide by `plugins/no-z-config.grit`. A Worker isolate is reused across requests, so a locale written into Zod's module-level error map during request A is still there for request B — a silent, unreproducible failure where one reader's validation error renders in another reader's language.

## Coverage is a `pithy doctor` check

Not a `pithy i18n check` command. For every locale you serve, every key reachable in the default locale must be reachable in that one too — through your catalog, the kit's translation, or a capability's own English. A gap is a local finding, it names the locale and the missing keys, and it fails `doctor`'s exit code.

```
i18n.supportedLocales.fr
  3 messages have no `fr` translation, so a reader in that language meets en instead.
  Add them to `i18n({ messages: { fr: … } })` in your `pithy.config.ts`: app/greeting, app/nav.settings, app/sign_out.
```

There is no account tier. Nothing about language is a question for the Cloudflare API.

## Configuring it

```ts
// apps/api/pithy.config.ts
i18n({
  supportedLocales: ["en", "es"],
  defaultLocale: "en",

  // Your own catalogs. One entry overrides one kit sentence; everything unmentioned
  // keeps arriving from the package with each release.
  messages: {
    es: { "auth/sign_in.title": "Entrar" },
  },

  // Ranges no truncation of a tag would reach. Historical pairs, and usually empty.
  exceptions: { nb: "no" },

  // The chains, in the order they are asked. `default` is the last resort either way.
  serverResolvers: ["param", "user", "cookie", "header", "default"],
  browserResolvers: ["query", "account", "storage", "navigator", "server", "default"],

  cookie: "pithy_locale",
  queryParam: "lang",
  storageKey: "pithy.locale",
});
```

The browser chain's `navigator` link reads `navigator.languages` — the browser's own `Accept-Language`, and the only link that answers for a first-time visitor who has chosen nothing and is signed in to nothing. It sits **above** `server`, which reads `document.documentElement.lang`: a scaffolded SPA is served from a static `index.html` that says `lang="en"`, so ranked the other way the browser link would never win and automatic negotiation would work on the server and nowhere else. A genuinely server-rendered app loses nothing by that order, because a server that negotiated did so from the same preference, and anything it knew that the browser does not — the reader's account — is ranked higher still.

Two chains, because half of each side's links do not exist on the other: `localStorage` is absent from a Worker, and `navigator.language` inside workerd is the constant `"en"`. The server chain reads `?lang=`, then the signed-in reader's `pithy_auth_users.locale`, then the locale cookie, then `Accept-Language` — as the **whole q-weighted list**, so `pt-PT;q=1.0, es;q=0.8, en;q=0.5` from a project with no Portuguese is a request for Spanish. A header full of `*`, `en_US` and empty tokens falls through to the default rather than throwing.

The `user` link reads `c.var.auth.locale`, which `@pithy-sh/auth` publishes off the user row its session lookup has already loaded — so it costs no query, and it works whichever order you list the two capabilities in. That last part is not a convention: the locale is resolved on the first read of `c.var.t`, by which time every `app.use("*")` middleware has run. Compose `i18n` without `auth` and the link simply contributes nothing, which is what an anonymous reader is.
