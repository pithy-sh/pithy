"@pithy-sh/auth": patch

Attaching and detaching a social provider are both recorded, and recorded when they happen. The trail carried `auth/oauth_linked` at `/link-social` — the moment the provider redirect is *minted*, before the person has seen a consent screen — so abandoning that screen, a provider refusing, or the freshness gate rejecting the link all wrote a success row for a link that never existed. Detaching one wrote nothing at all: there was no `auth/oauth_unlinked` code and nothing on `/unlink-account` emitted, so a provider was removed and the trail was silent. Between the two, "which providers can sign in as this account today, and when did that change" was unanswerable from the record that exists to answer it.

Both events now come from the account row rather than from an endpoint. Better Auth reaches that row from four directions — `/callback/:id` on a first social sign-up and on a link, the OAuth linking path, `/unlink-account`, and the cascade that drops every account when a user is deleted — and all of them pass through the `account` database hooks, so one pair of hooks covers what four endpoint wirings would have had to enumerate and keep current. It is the seam the session-revoked hook already used, applied to the other table: a handler wired to one endpoint misses the others, and the row is what the fact is keyed by. An abandoned link now emits nothing, because nothing happened.

Neither row carries a token. The hook payload holds the provider's access, refresh and id tokens beside the three columns the event needs, so the emitter parses it into a named Zod object first — the strip is the guard, not a rule somebody has to remember, and no later edit spreading "the account" into `metadata` can leak one. A row carries the provider slug, the account row id and the user; the provider-asserted email is not stored on that row and does not start being stored now. A `credential` row is not an OAuth link and emits neither event.

An event's actor is whoever caused it, which is not the account it concerns. The `delete.after` hook fires on *every* removal, the user-deletion cascade included, so attributing the row to the account's owner said that person had detached their own providers — from whatever address the operator deleting them was calling from, since the request headers in scope were the operator's. A trail that misattributes an actor is worse than one that is silent, because it reads as evidence. There are three cases and only three, and they are about the caller rather than about the cascade: an authenticated caller is `user` and is named; a request holding no session (a first social sign-up completing at `/callback/:id`, a server-to-server call) is `anonymous`; nobody calling at all is `system`, with no actor id and no address borrowed to stand in for one. Whose link it was is a different question and rides in `metadata.userId`, so the two are free to disagree. Every shape is driven through `internalAdapter.deleteUser` rather than described in a docblock.

A first social sign-up writes `auth/oauth_linked`, and that is a deliberate reversal of the rule the endpoint wiring carried. That rule — "mapping it here would mislabel every first sign-up as a link" — was true of a *path*, which cannot tell a sign-up from a link. From the row it stops mattering: the event claims a provider can now sign in as this user, and a first social sign-up is exactly when that becomes true. It is pinned by a test, so the next reader finds a decision rather than an absence.

Two concurrent unlinks of one account record one removal. Better Auth's `deleteWithHooks` reads the row, deletes it, then runs `delete.after` gated on the row it *read* rather than on a row it removed, so both callers reached the hook. The claim is now the delete itself — issued in `delete.before`, where SQLite serializes the two statements and exactly one reports a removed row — and only that caller emits.

**A refused request is never recorded as a success.** `GET /auth/token` with no credential answered 401 and wrote `auth/token_refresh outcome=success`; `POST /email-otp/send-verification-otp` with an invalid address answered 400 and wrote `auth/otp_sent outcome=success`. One cause, not two: Better Auth catches an endpoint's `APIError` into a result and runs the endpoint `after` hooks over it anyway (`api/dispatch.mjs`), so from the hook a refusal is indistinguishable from a request that worked. Every audited path was exposed, not the two that happened to be probed — so the fix is `emitAfterRequest` reading `ctx.context.returned`, and a refusal now writes `denied`, which is first-class in the audit schema and is the row an abuse count is made of. The gate walks the path table as a whole: a fifth entry added tomorrow is covered the day it lands.

`POST /sign-out` with no session is the same defect in its quieter form. It answers `200 {"success":true}` whether or not it found a session to delete, so an expired cookie, a bearer token (which it does not read) or a bare `curl` each wrote a sign-out that signed nobody out. The endpoint was not lying; the event was. Each audited path now declares what must be observably true for its action to have happened, and `/sign-out`'s is a session row disappearing — which also, finally, names the person it was about, since that endpoint declares no session middleware and had been recording every real sign-out as `anonymous`.

**A non-2xx is sufficient evidence of a refusal and is nowhere near necessary**, and reading the status alone left one path still lying. `POST /email-otp/send-verification-otp` declines to send and answers `200 {"success":true}`: Better Auth drops the verification row and returns success rather than confirm that an address is registered, and the kit's own `sendVerificationOTP` returns without queuing anything for any `type` but `sign-in`. Both are deliberate, neither is visible from the response, and both wrote `auth/otp_sent outcome=success` for a send that never happened. So there is no longer a path that claims its response is its own evidence: every entry in the table names something that must have *happened* — a session row gone, a message handed to the email seam, a token in the payload — and a completed response without it writes `denied`, or nothing where nothing was attempted. The entry cannot be added without naming evidence somebody knows how to observe, which is a compile error rather than a review note, and the suite walks the table rather than listing the endpoints that were probed.

**The evidence was marked before the send was awaited, and the send's answer was thrown away.** `SendAuthEmail` returned `Promise<void>`, and the mark went in at the call rather than after it — so the whole of what `@pithy-sh/email` decides underneath was invisible to the two events that claim a message. Two of those decisions are live on the default composition for an unauthenticated caller. A recipient on the global suppression list has the message **withheld**: `enqueueEmail` starts nothing and marks the job row `suppressed`, and `auth/otp_sent outcome=success` was written for it. An enqueue that simply **fails** — no jobs table, no binding — throws into Better Auth's `runInBackgroundOrAwait`, which logs and lets the endpoint answer `200 {"success":true}` anyway; the queue was empty, and the row still said success.

So the seam answers what happened. `SendAuthEmail` returns `queued`, `withheld` with a reason, or `failed`, the mark goes in after the await, and a throw is marked and re-thrown rather than swallowed — nothing here decides a status, it records what happened under one. Marking early had been justified by `runInBackgroundOrAwait` possibly deferring the callback past the response; it defers only when `advanced.backgroundTasks.handler` is set, which the kit never sets and an adopter cannot, so absent one it awaits and the mark still lands before the `after` hook.

**A withheld message is not a failure, and the row says which it was.** A suppressed recipient is the email capability working exactly as designed, so that row is `denied` — core's word for a rule that declined to act — and carries `metadata.reason`, the capability's own suppression reason, because "suppressed" alone does not say whether the mailbox is dead, the person complained, or an operator did it by hand, and those are three different next moves. A failed enqueue is `failure`, severity `warning`, carrying a fixed reason and never the thrown error's own text: an audit row is long-lived and queryable, and a thrown message is the one value in reach that nobody has vetted. Recording a fault as a decline would send somebody hunting an abuser while a binding is missing. A queued send carries no reason at all.

`SendAuthEmail` is internal, so widening it breaks nothing an adopter holds: it is produced by `makeSendAuthEmail`, consumed by the kit's own plugin callbacks, and wired from the composed email capability's `enqueue` — `AuthWiring.enqueueEmail` is filled by `compose`, never by hand — and it is not in the package entry. `undispatched` counts as a send, deliberately: the job row exists and the scheduler drains it once a host is deployed, so the deployment gap is the email capability's own thing to report rather than a decline in a column an abuse count is read from.

**The enumeration guard survives the audit trail knowing better.** That endpoint answers 200 so a caller cannot tell a registered address from a stranger's, and none of this changes what the caller is told: the emitter is an `after` hook that writes a row and returns, and the row names an action, an outcome, an actor and an ip, never an address. The acceptance drives a registered and an unregistered address through the same configuration and asserts the two responses are identical in status, in every header, in the body and in its byte length, while the trail records a send and a decline — and it does the same for a suppressed address against a sending one, which is the pair the new answers are able to separate.

Two docblocks said the opposite of what the code does, and are corrected against the behavior rather than trimmed. `deleteWithHooks` resolves its context from `getCurrentAuthContext()`, which is async-scoped to the dispatch — so a user-deletion cascade reached through an endpoint carries that endpoint's session and headers, and the operator who drove it is named as the actor of every row it writes, correctly, with their address. The prose claimed a cascade is "nobody" and that `system` is what a cascade looks like. `system` is what *no request* looks like: a script, a queue consumer, a migration. What holds everywhere is the narrower rule underneath it — the account's owner is never the actor merely for owning the row, and rides in `metadata.userId` instead. Both shapes are now driven, an operator's console endpoint and a server-to-server call, so the sentences cannot drift back.

The acceptance is against a real instance over real D1 in the workers runtime, and every case asserts a table alongside the event — a trail that disagrees with the account table, the session table or the email queue is the defect, not a passing test. `/link-social` is driven over HTTP to prove the minted redirect writes no success row, the refusals are driven over HTTP to prove the endpoint's own error reaches the emitter, every send is checked against `pithy_email_jobs` rather than against the marker the emitter reads, the suppressed recipient is driven through the capability's own suppression table and the failed send through the jobs table genuinely not being there, and the no-token gate plants all five sensitive columns on the row — `accessToken`, `refreshToken`, `idToken`, `scope`, `password` — and asserts they are stored before asserting they are absent, because four of them had been null and passing for free.

**One defect, two producers, and the second is why the fix moved down a level.** Better Auth's `deleteWithHooks` reads the row, runs `delete.before`, issues the delete, then runs `delete.after` gated on *the row it read* — never on the delete having removed anything. The unlink race above was the first thing that produced: two `/unlink-account` calls, one removal, two `auth/oauth_unlinked` rows. It was fixed where it was found, on the `account` hooks, and that was the wrong altitude. `/sign-out` reaches `internalAdapter.deleteSession(token)` and the same primitive, so concurrent sign-outs on one cookie all found the row, all issued a delete, exactly one removed anything, and all of them fired `session.delete.after` — `markSessionEnded` ran for each and `emitAfterRequest` wrote `auth/signout outcome=success` for callers that signed nobody out. Two hooks, one hole, and a third `delete.after` wired the obvious way would have been the third.

So the guard is a primitive: `claimedDelete` builds the `delete` hook pair, issues the claim in `before`, and runs the supplied `after` only for the caller whose statement removed the row. The row's existence is the only single-winner fact available, so the claim *is* a delete — the same gate `consumeSession` already uses for concurrent token rotations. Better Auth's own delete then removes nothing, which it neither checks nor reports: `deleteAccount`, `deleteSession` and the user-deletion cascade all discard the count, so its control flow is untouched. Handing back a pair rather than two loose functions is the point — there is no `after` to register without a `before` beside it, and the `after` carries a private brand a survey can see.

`onSessionRevoked` is inside that gate rather than beside it, because at-least-once still holds under it: the only way a claim loses is that another caller won it, and that caller runs the handler. What it buys is that tenancy hears about one removal once.

**The gate is about the invariant, not about the two hooks that have one today.** `surveyDeleteHooks` walks whatever models a `databaseHooks` object holds and names every `delete.after` that did not come out of `claimedDelete`; it has no list of models of its own, so a third one added tomorrow is covered the day it lands. It reports what it *found* alongside what it faulted, and the gate asserts both — a check whose subject has gone missing would otherwise pass by finding nothing, which is the one failure a gate must not have. Its reach stops where `makeAuth`'s own hooks stop: an adopter's plugin registers database hooks separately, they never reach `options.databaseHooks`, and one wiring an unclaimed `delete.after` has the same defect with nothing here to say about it. That the survey can fail at all is established against hooks objects written in a test — a `before` that does something else, an `after` that borrowed a claimed `before`, an impostor declaring a flag — rather than from the instance it is pointed at.

**What remains the dependency's, stated because it is not fixed and will not be from here.** The kit does not own `deleteWithHooks`; every `delete.after` Better Auth runs, including those of any plugin an adopter composes, still fires on a row that was read. Upstream already has the right shape in `consumeOneWithHooks`, which gates its after hooks on the consume — it has simply not been applied to `deleteWithHooks` or `deleteManyWithHooks`. And claiming by pre-empting the delete carries two preconditions that hold in this composition and are checked per model rather than assumed: no `delete.before` veto runs after the kit's own (plugin hooks are registered first, and `deleteManyWithHooks` running every row's `before` ahead of the delete is where that would show), and the delete being pre-empted is a real delete — Better Auth's `endPreservedSessions` passes a `customDeleteFn` that expires a row instead of removing it, and `consumeOneWithHooks` reads the row it is about to consume, so neither could take this claim. Neither is reachable here, with one adopter-reachable way to break the second that is worth naming rather than implying: a plugin's `init` may return options, `runPluginInit` merges them under the instance's own with `defu`, and the instance sets nothing for `preserveSessionInDatabase` — so a plugin turning it on would have session rows removed where Better Auth meant to expire them in place. `ClaimableTable` is the list of models for which that has been checked, and a model added to it is a decision rather than a spelling. The claim also costs one extra statement per removal, and a cascade over N sessions now issues N deletes where it issued one.
