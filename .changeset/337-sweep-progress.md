Stop one bad Paddle event from holding the whole stream, and stop asking every adopter for a permission only refunds need.

**A failure now costs a bounded number of runs, then a quarantine.** The last fix stopped writing `processedAt` beside an error so a failed event would be retried, and halted the cursor in front of it. That is right for a transient fault and wrong for a permanent one: a malformed event, a deleted transaction, a shape Paddle changed, and the sweep stands in front of it forever — at which point every later purchase is the one nothing ever finds. Neither "always skip" nor "always halt" is the answer, so the event row carries an `attempts` count and the sweep halts three times — three days, on a daily cron — and then marks the event processed with an error that names the quarantine, the attempt count and the last failure, and moves on. The count lives on the row because it is a fact about that row's handling, alongside the `processedAt` and `error` it is only ever read with. `PaddleSweepReport` gained `quarantined`, so a run that gave up on something says so.

**`include=adjustments` is asked for only by the read that needs it.** Every transaction read sent it, and the docstring claimed a key without adjustment-read permission "simply gets no array back rather than a refusal". Paddle's permissions reference says the opposite — an `include` demands read permission on the entity included, and answers `forbidden` (403) without it — and the OpenAPI spec carries the same fact as `x-enum-permissions`. So a narrowly scoped key, which this kit tells adopters to use everywhere, had every transaction read fail. Only the adjustment map asks for the array now; checkout, verification and reconciliation work on `transaction.read` alone. The requirement is documented where it is real, and a refusal from the refund path names `adjustment.read` rather than leaving an operator to guess.

**One unreadable transaction no longer discards its page.** `sweepPaddleEvents` parsed every event before returning and ran outside the caller's per-event guard, so one failed transaction read threw away the events ahead of it that had read perfectly. An event that cannot be read now comes back carrying its failure, and the caller halts at that one event.

**The module doc no longer claims a safety net that does not exist.** It said this sweep was the only repair for a delivery that arrived and failed. It is not: `completeWebhook` sets `processedAt` even when it records an error, and the sweep reads freshness off that column, so the rows the claim named are exactly the rows it skips. Nothing in this package repairs a failed delivery today. `completeWebhook` is pre-existing across all four rails and is reported, not changed here.
