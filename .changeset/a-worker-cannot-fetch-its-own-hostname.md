A project that administers itself gets a service binding to itself. A Worker cannot fetch its own hostname — the subrequest loops back through the edge into the Worker it came from and hangs until Cloudflare answers 522, on a route that answers in a second and a half from outside — so the call has to be dispatched inside the runtime instead. Declare `administersItself: true` in the root `pithy.config.ts` and `pithy provision` writes a `SELF` entry into every stanza it generates, pointing at the script that stanza deploys as; the app reaches itself with `env.SELF.fetch(request)` and reads the binding's name off `@pithy-sh/core`'s `SELF_BINDING` rather than agreeing a string by hand. Feature environments are the reason this belongs to the kit: their stanza is regenerated on every `pithy provision --feature`, so an entry added by hand never survives to the deploy, and the script it must name is composed from the branch. The entry is written from the same `name` the writer settles in the same edit, so the two cannot disagree, and a re-run retargets in place rather than duplicating. `pithy worker rename` carries the entry to the renamed script, and `pithy doctor` names a declared self-administering project whose stanza binds no `SELF` — or binds one to a script that stanza does not deploy as — and fails the exit over it. The top-level `dev` stanza is deliberately left alone: the loop that ends in a 522 needs the edge, and a Worker reaching its own address locally is an ordinary request. A project that declares nothing gets no binding and no change to its stanza.
