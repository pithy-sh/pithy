A secret write knows where the value goes, and `pithy secrets rm` performs the revocation it reports.

`SecretWriteRequest` carried no `backend`. Every write therefore reached the environment's manager Workflow, which writes one place: the encrypted D1. So `pithy secrets create STRIPE_SECRET_KEY --env prod` exited 0, printed a success line, and left an encrypted row no reader ever opens — the Secrets Store entry the Worker actually binds stayed absent. `pithy secrets rm CFS_ENV_MINT --env staging` printed `CFS_ENV_MINT removed from staging.` and deleted that same shadow row while the live entry stayed present and stayed bound in `wrangler.jsonc`. An operator revoking a leaked credential was told it was gone while the Worker kept reading it.

A request states its backend now, and one router turns that into a writer. A `d1` secret goes to the manager Workflow, unchanged. A `cf-secrets-store` secret is written straight into the account's Secrets Store, at the `<project>-<env>-<secret>` entry composed by the same code `pithy secrets provision` looks it up with — so what you write is what gets bound. `create` refuses a name already there and `update` refuses one that is not, in both stores alike, and `rm` deletes the entry the Worker reads. The manager's dispatcher refuses anything but `d1` rather than accepting it: a write path added later that forgets to route fails at the first dispatch instead of quietly filling a database with values nothing looks in.

**That closes the four cells that had no command at all** — a `cf-secrets-store` secret, environment- or global-scoped, whose value is one only a human holds: an OAuth client secret, a payment rail's key, a shared HMAC key, an adopter's own `bootstrap` value. Every Secrets Store write site in the kit composed its own value and none accepted one you were holding, which is why four rounds of naming a different command each failed. `pithy secrets create` is the command, and `pithy doctor` names it again.

**`rm` also says what it cannot do.** The entry is gone; the Worker's `wrangler.jsonc` still carries the `secrets_store_secrets` line naming it, and nothing in the kit removes one, so the next deploy of that Worker fails until the binding goes or the value comes back. That prints under the removal rather than being left to be found.

**`SECRETS_ENCRYPTION_KEYS` is refused in all three modes.** It is the master key every other secret in an environment is sealed under: `create` and `update` orphan all of them, `rm` loses them. Before the write path knew its backend the damage was quieter and no smaller — a master-key-shaped value was written as a versioned envelope into the very database the master key opens. `pithy secrets provision` creates it when it is absent, and that is the only thing that writes it.

**`pithy provision` and `pithy doctor` give one answer about a missing entry, not merely one renderer.** They had a renderer each, and a reviewer running both to completion on one project found doctor's corrected and provisioning's still naming the dead end. Sharing the renderer was the first fix and was not enough: there are two answers — `pithy secrets provision` for an entry the kit composes a value for, `pithy secrets create` for one only you hold — and provisioning went on asking for the second every time. So it told an operator to hand-write `SECRETS_ENCRYPTION_KEYS`, which `pithy secrets create` refuses outright, and that is the entry a bare `pithy provision` most reliably reports unbound. One function decides now, over the registry facts both reports read, and both are driven over every cell and compared. The `--env` flag is on the command only where the write rule accepts one, which is what the third attempt at this line got wrong. The Dev secrets block asks `isProvisionableSecret` rather than reading the `bootstrap` axis, so both halves of that report answer *what creates this value* the same way. And `devSecrets.bootstrapUnmintable` is pinned: `doctor.md` documented it for adopters while nothing held the payload to it.

**A `bootstrap` secret's entry holds the value, not an envelope around it.** The store writer wrapped every value in the `{ currentVersion, versions }` envelope the ordinary reader decodes. That is wrong at the root for a `bootstrap` secret, which is *defined* as one read before the store that decoder needs is open: `resolveEncryptionConfig` takes the binding's plaintext, parses it, and has no decode step an envelope could survive. So `pithy secrets create` on such an entry reported success over a value the Worker answers `is not a valid EncryptionConfig` to, at its first request. `#323` settled the identical question for the dev secrets file and stated the rule generally — the destination receives the payload, not a wrapper — and one function makes that decision for both destinations now. The test is the far end rather than the shape: a real write, then the real boot reader parsing what it stored.

**`pithy secrets rotate` writes where the registry says the secret is held.** It was the one value-touching command left off the router, because a rotation also needs the ledger and the ledger is the manager's alone. A `cf-secrets-store` rotation therefore ended in a 500 raised at the store write — and with a `provider` rotator that write is *after* the issuer has rolled the credential, so the kit asked a provider for a new secret, received it, and threw before storing it. Rotation is routed now, and everything refusable is refused before the issuer is called: an unreachable Secrets Store and an `update` of an entry that is not there are both facts about the destination, both knowable in advance, and both were being discovered at the write.

**And a `d1` rotation asks the same questions, which it did not.** The pre-flight landed on the Secrets Store writer alone; the manager's dispatcher implemented none, the router asked for one with `?.`, and an absent method resolved. So on the more common backend the ordering was exactly what the pre-flight had been added to prevent: the rotator ran, the issuer rolled the credential, and the dispatched `update` came back `Secret 'X' does not exist` — the old credential dead at the issuer, the new one existing only in the process raising that error. The manager is asked now, through the one mode of its write Workflow that writes nothing, so *is this manager there* and *is this secret there* are both answered while the previous credential is still live and the command can simply be run again.

**A backend that skips the pre-flight is a compile error.** That is the actual repair, because one writer having the guard and the other not is how this survived a fix aimed at it. Every route on the router is a `PreflightSecretDispatcher`, and so is what `pithy secrets rotate` accepts — a backend with nothing to refuse in advance says so through `withoutPreflight`, in words, with a reason. The ordering is a property of the dispatcher rather than of whichever writer happened to be written carefully.

The rotation tests assert the **order of the calls**, on both backends, through the real `rotateSecretValue` and the real writers: the rotator is called zero times when the destination refuses, no ledger row is opened, and the credential the issuer holds is untouched. An exit code proves nothing here — the command exited non-zero throughout, *because* the credential was gone.

**A `global` Secrets Store write says what it changed.** It reported the environment it was dispatched through — the canonical one, an implementation detail — when what changed is the single account-level entry every environment's stanza binds. `payments-provider-credentials written to prod` understated it by every environment but one, and an operator who then went to update staging separately was acting on a report of work already done.

Every test on this surface now asserts **where the value landed** — a recording Secrets Store and a recording database, table-driven over every backend, scope and origin a registry can hold — rather than that the command exited 0. Every previous test here passed on the exit code, which is exactly why all of this survived four rounds.
