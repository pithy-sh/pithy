Settle what an orphan is, so the two paths that write its row agree.

#337 established that `processedAt` means *finished with*, and that a delivery which arrived and failed keeps it null so a redelivery or a replay can repair it. The Paddle sweep did not follow. It called `complete` on an orphan — an event with no `pithy_user` stamp, for a customer with no `provider_accounts` row — and its own doc said so on purpose. Both paths write the same row under `UNIQUE (rail, providerEventId)`, so whichever reached the event second saw what the first wrote. When the sweep got there first, the account linked, and Paddle redelivered, the guard read `processedAt` and answered `duplicate`. The purchase was never projected.

An orphan is repairable. Nothing about the event is wrong; the world is missing a row that a checkout, a client submission or an operator will add. So the sweep abandons it rather than finishing it. `abandonedAt` is already the state for exactly this pair of answers: invisible to the sweep, so the cursor advances and one unlinkable customer does not stall every event behind them; not finished to the guard, so the delivery that follows the link still projects. It costs no attempts — no number of sweeps conjures a link, so the first look is as informed as the tenth. The run's report names the orphaned event ids rather than folding them into `ignored`, because a stuck sale must not read as a healthy number.

The webhook path had the mirror of the same confusion. `completeWebhook` withheld `processedAt` whenever a reason was present, which meant a delivery carrying no transaction state was finished when the rail said nothing about it and outstanding when the rail explained why — a partial refund that takes nothing away, a token Play will not show us, a subscription Lemon Squeezy no longer knows. The explanation was the only difference, and an explanation must not be able to change a state. It cost the two things the column is read for: a null `processedAt` under an old `receivedAt` is the drift signal, and the short-circuit is what makes a retry storm cost one insert instead of a projection. Four of the five rails have no repair pass, so those rows never settled. The outcome is now three cases, not two: projected, finished with a note, and repairable with an error.

`SweptEvent.failure` also carried its body to D1 without passing `recordedPayload`, the allowlist that keeps an unredacted Paddle client token out of `pithy_payments_webhook_events`. It was harmless because every type that can reach that branch is on the recorded list, but that is two lists agreeing rather than a control. It goes through the allowlist now, and the subset it was leaning on is asserted rather than assumed.
