A freshness window that is not a number is refused, rather than honored as no window at all.

Security: a webhook tolerance of `NaN` or `Infinity` removed replay protection instead of widening it. `skew > NaN` is `false`, so a correctly signed delivery of any age verified — a captured Stripe or Paddle webhook replayed indefinitely, and a captured Google Play Pub/Sub push token did too. The realistic source was never a hostile caller: `Number(env.STRIPE_WEBHOOK_TOLERANCE)` on a variable that is unset or misspelled is `NaN`, TypeScript types it `number`, and each layer below re-applied its own default with `??`, which catches `undefined` and never `NaN`. The same shape sat one operand over in Apple's chain check: an invalid clock made `at < notBefore` and `at > notAfter` false alike, so every certificate in a chain passed the check that says a certificate is still in date. Two `@pithy-sh/secrets` numbers failed the same way — a non-finite `secretsCacheTtlSeconds` made the shared secrets cache never expire, serving a rotated-out secret for the life of the isolate, and a `ROTATION_INTERVAL_DAYS` that did not parse made at-rest master-key rotation never come due, silently, on every cron tick.

**What to check.** Anywhere a number or a clock reaches one of these knobs from an environment variable, a computed value, or anything other than a literal: `toleranceSeconds` on `requireSignedWebhook` / `verifySignedWebhook` / `checkSignedWebhook`, `toleranceSeconds` on `stripeRail`, `freshnessSeconds` on `paddleRail`, `paddle.webhookFreshnessSeconds` in `pithy.config.ts`, `clockSkewSeconds` on `verifyGoogleOidcToken`, `now` on `verifyCertificateChain`, `secretsCacheTtlSeconds` on the `secrets` capability, and the `ROTATION_INTERVAL_DAYS` var on the secrets manager Worker. A project whose webhook endpoints have accepted deliveries that predate their own tolerance should treat those deliveries as unbounded in age and lean on the uniqueness key rather than the window — `@pithy-sh/payments` records every delivery under `UNIQUE (rail, providerEventId)`, which is absolute and was never affected.

Each of those is now checked before anything is compared, and refused rather than clamped. The freshness window gained a ceiling with it: `SIGNED_WEBHOOK_MAX_TOLERANCE_SECONDS` (3600), because a tolerance is a replay window in the plainest possible units and every second of it is a second longer a capture keeps working. `@pithy-sh/secrets`' cache lifetime gained `MAX_SECRETS_CACHE_TTL_SECONDS` (3600) on the same argument, and for a second reason: there, `Infinity` is only the loud spelling of a pin, and an hour written in the milliseconds the option is not measured in outlives any isolate.

**Every refusal is `core/internal`, and it now stays `core/internal` all the way out.** A misconfigured endpoint is our fault, not the sender's, and the payments webhook guard was catching these and re-rendering them as `payments/webhook_unverified` — a 401 telling an operator to check the signing secret, over a number we wrote, plus an audit row claiming a forgery had arrived when none had. That is worse than silence: it names a culprit, and the culprit is us. The guard's pass-through set now carries `core/internal`, `core/upstream_failed` and `core/upstream_timeout` beside the two `payments/*` codes that were already there, so a 500-class code keeps its status and its meaning — *read our logs*. The client boundary is unchanged: these still leave through `clientError`, which strips `action` and `detail`, so the sender learns a status and a bland message and the knob's name reaches only the terminal, the `--json` line and the log.

**Where the refusal fires is a blast-radius decision, and it lands on the route rather than on boot.** `paddle.webhookFreshnessSeconds` is deliberately *not* bounded in `PaymentsPaddleSettings`: that schema parses at module scope, so refusing there refuses the whole Worker — every route, including the ones that have never heard of Paddle — for one webhook knob, and a project that had legitimately set a wider window would have met that as a dead deployment on a patch upgrade. The bound is enforced in `verifyPaddleSignature` instead, which is the only path that compares the number and cannot be reached around, so an over-wide window costs the Paddle webhook endpoint alone while Paddle keeps redelivering. Fail closed, for one route. The shape checks stay where they were: a `NaN`, a fraction or a negative is still refused by the config schema, as it is for every numeric field in the kit.

**A fifth instance, in `@pithy-sh/leaderboard` — and it fails both ways.** `LEADERBOARD_LOCK_STALE_MS` is an operator-typed wrangler var the rank-refresh Workflow read as `Number(env.…)` and handed straight to the advisory lock's takeover clause. **Zero or negative fails open**: `staleBefore` lands at or after `now`, the `WHERE acquiredAt < staleBefore` is then true of *every* row including a fresh one, and each cron fire steals the lock from the instance still holding it — at-most-one is gone, two refreshes interleave their chunked rank writes, and every board reads as ranked while its ranks are duplicated and gapped. **`NaN`, `Infinity` or a value past the JS date range fails obscurely**: the horizon becomes an Invalid Date, `SQLiteDate`'s encode side refuses it, and a `ZodError` reading *"expected date, received Date"* leaves `acquireRefreshLock` outside any Workflow step and kills the run on every fire, naming nothing. `requireLockStaleMs` now refuses anything that is not a whole number of milliseconds from 1 to `MAX_LOCK_STALE_MS` (one day), as `core/internal` with the var named in the action line — checked inside `acquireRefreshLock`, which is the only thing that reads the number and cannot be reached around, and again where the string becomes a number so the refusal can name the var. The ceiling is not decoration: the default written in the wrong unit is forty-one days of a crashed instance's lock never being reclaimed, which is boards that quietly stop moving.

**The operator's remedy now reaches a surface.** Every refusal above carries an `action` naming the variable to fix, and in a deployed Worker that `action` reached *nothing*: `clientError` strips it on the way to the wire — correctly, and that has not changed — the terminal renderer is a CLI surface no Worker runs, and the request produced exactly one record, the access log line reading `status: 500`. So the refusal was right and invisible, which is the unfollowable-action defect one layer out. `createBackend` and the email host now register `loggingErrorHandler` (`@pithy-sh/core/src/logger/errorHandler`) instead of the bare `pithyErrorHandler`: it writes the fault to the request logger with its full payload — `action` and `detail` included, correlated by the `request`/`method`/`path` fields already bound — and then renders the identical response. It lives on the logger's side of the boundary rather than inside `error/http.ts`, because `logger/boundary.test.ts` gates that the client-facing error surfaces never import the logger, and that decision is deliberate; the encoder is imported *by* the logging handler, never the other way round. **A 5xx logs at `error` and a 4xx at `debug`** — a 4xx is the caller's, its status is already in the access log line, and an unauthenticated caller must not decide how much a Worker writes. `pithyErrorHandler` stays exported for an app with no logger seam.

**And a gate, so there is no sixth.** Two deliberate sweeps missed two instances, so `packages/cli/src/ci/environmentNumbers.test.ts` fails the build instead of relying on a reader: every `Number(env.…)` / `parseInt(process.env.…)` in shipped source must be the *whole* of one argument to a named function declared there as refusing a value it cannot compare, and each declared row is itself checked for still having a finiteness check and a throw — an allowlist that cannot rot into a rubber stamp. It says plainly what it cannot catch, which is most of the space: a value that is already numeric when it arrives (a Zod-parsed config field, a JSON var, a D1 column, a function parameter — `secretsCacheTtlSeconds` and `verifyCertificateChain`'s `now` would both be invisible to it), a comparison built from two unvalidated numbers, anything computed, `env` reached under another name, and unary `+`. It catches exactly the shape that shipped five times.
