A feature deployment signs people in on Cloudflare's always-pass test keys, with nothing to provision and no adopter edit.

`POST /auth/sign-in/magic-link` on a branch deployment answered `500 {"code":"turnstile/config","message":"Turnstile is not configured."}`, and so did every other protected route. Two halves of one cause. The sitekey lookup was a closed object of `dev`, `staging` and `prod`, so a feature build read `undefined` and the client projection returned `{ enabled: false }` — no widget rendered. And nothing had ever written the widget *secret* for a branch: `pithy turnstile provision` writes dev's secrets file and staging's and prod's stores, while `pithy provision --feature` creates the branch's own store empty, because a widget secret is obtained from Cloudflare rather than minted. There was no edit that would have fixed it either: a feature's config and store are generated per branch, and nobody owns them.

A feature deployment is ephemeral and holds no real users, so the pair it wants is the pair dev already wires. `TurnstileSitekeys` now carries an optional `feature` key, and a build left with none resolves Cloudflare's documented always-pass sitekey for the widget's mode; the gate resolves the matching always-pass secret the same way when the store holds none. Both are defaults rather than writes, so `pithy turnstile provision` still writes exactly `dev`, `staging` and `prod` and a project scaffolded before this key existed provisions unchanged. State `feature` to run a real widget on a branch, or `""` to render none. `dev`, `staging` and `prod` resolve what they state and nothing else, and an environment that merely looks like a feature's — a declared `live`, a `preview`, `features` — still renders nothing and still refuses: `feature` is the one stanza name a branch's provisioning writes and `DeclaredEnvironments` refuses, so it cannot be an adopter's environment.

The gate accepts a test key's verdict in a feature as it does in dev — Cloudflare's own `metadata.result_with_testing_key`, and the action-less answer that flag comes with — and refuses one in `prod` or an unstamped Worker exactly as before. `middleware.workers.test.ts` proves the defaulted secret against live siteverify, which is the only thing that can say the string is genuinely Cloudflare's, and `turnstileBundle.test.ts` runs a real `vite build` for a feature and reads the sitekey out of the bundle.

**A gate with no widget secret now names what is missing and which environment it is missing for.** `Turnstile is not configured.` was true of every environment at once, and an operator holding it had to find out which by elimination. The refusal reads `The humanity check has no widget secret for the prod environment.` — the environment in `message`, because that is the field the HTTP codec lets across; the secret's registry name, the reader's own failure and `pithy turnstile provision` in `detail` and `action`, which stay in the Worker. It is still `turnstile/config`, still fails closed, and the selection refusals a route earns for itself — which widget this route gates, and the pair that needs a `mode` — are untouched.

`pithy doctor` no longer reports a feature build as an environment no sitekey can reach, because it is not one any more; a `feature: ""` an adopter wrote is reported as the blank sitekey it is. `pithy turnstile provision` says a feature is covered by the same pair and needs nothing, and its `--json` `environmentsWithoutSitekeys` names only declared environments beyond the four.
