`doctor` no longer tells you to promote every unexplained `.dev.vars.local` key. A key named like a binding the Worker's `wrangler.jsonc` declares — any kind, at the top level, in any `env.<name>`, or in `previews` — is its own finding, and never goes into `vars`: wrangler refuses a config where a var and a binding share a name. The line names the Worker and the binding's kind, and says what dev does with the value: wrangler dev ignores it where the binding is at the top level, and hands the string over where the binding is only in an environment or a preview. It says remove it. In the root file, which reaches every Worker, it names each Worker that binds the key, and says move it into the files of the Workers that read it as a value, when one does. Each Worker's own file is judged against that Worker's secrets, bindings and vars, so a sibling's secret no longer hides a binding. A name in wrangler's `secrets.required` is a secret: it reads as shadowing one, never as dev-only. Any other dev-only key gets both outcomes, because doctor cannot know which is true: declare it in `wrangler.jsonc` `vars` if production needs it, delete it if nothing reads it. The root `.dev.vars` check says the same of a key named like a binding: delete it, never copy it into `dev.json`. `--json` carries the new finding as `devVarsLocal.shadowingBinding`, and the root `.dev.vars` one as the `bound` state.
