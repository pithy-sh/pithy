"@pithy-sh/cli": patch
---

A globally installed `pithy` resolves capabilities against the project, not against itself.

`pithy payments provision` on a project with `@pithy-sh/payments` installed, composed in `pithy.config.ts`, and typechecking against it answered *"The payments capability is not installed. Run `pithy add payments`."* Both halves of that sentence were wrong, and the action was the worse one: `pithy add` scaffolds into `pithy.config.ts`, so an adopter who trusted it rewrote a hand-built configuration to work around a resolution bug.

Every capability module was reached with a bare specifier — `import("@pithy-sh/payments/src/capability")` — and a bare specifier in ESM resolves relative to the **importing module**. So the CLI read the project's config, learned which capabilities the project composes, and then asked its own `node_modules` about them. The split was exactly the CLI's own dependency list: a global install could provision `email`, `secrets` and `turnstile` and nothing else. A local install worked only by accident of location, because `<project>/node_modules/.bin/pithy` starts inside the project.

The quieter half was the packages that *did* resolve, to the CLI's copies. A global cli 0.2.2 ran `@pithy-sh/email@0.1.7`'s resolver against a project pinned to `0.1.6`, silently, because every brand check in the kit is structural and structure did not change; what drifted was resolver behavior and the contents of the Worker that got deployed. `project/kitSource.ts` had the same defect with no error at all — `import.meta.resolve` returned a real, existing path to the CLI's own copy of a host worker, so `pithy <capability> provision` under a global CLI deployed the CLI's worker under the adopter's name.

Fifteen files carried it, three more than the issue's own survey found. Every one now resolves from the project root the config was read from, through one resolver (`project/kitResolve.ts`), and `ci/kitResolution.test.ts` holds the property as a set in both directions: a bare `@pithy-sh` import under `packages/cli/src` either goes through that resolver or is written down there with its reason. The only sites written down are `@pithy-sh/cloudflare`, which is not a capability — no manifest, no catalog entry, no `pithy add cloudflare` — and which an adopter's project therefore never installs.

`pithy` no longer says "not installed" about a package that is in the project's `node_modules`, and never prints `pithy add` for one. An installed package that will not load names `bun install` and the package to upgrade instead — the remedy that can work — and a resolver error carrying an absolute path is reported as an incomplete install rather than interpolated into the remedy.

Two checks stop lying as a result. `pithy doctor`'s binding-scope check reads a capability's resource namer through a guarded import specifically so it answers under version skew — *a newer CLI beside an older `@pithy-sh/email`* — and reading it from the CLI made it compare the CLI's answer with the CLI's answer, going quiet on exactly the installs that have a split. And CLI audit resolved `@pithy-sh/audit`, a `devDependency` that a published tarball does not ship, so a global install recorded **nothing** for every project composing `audit` — no message, no exit code, and a security-relevant action with an audit trail the adopter believed was on.

**A capability installed under the Worker that composes it is reached, not refused.** The first pass read "the project" as one directory, which left the issue's own sentence reproducible in the layout the kit tells adopters to adopt: capabilities are per Worker, `apps/api/pithy.config.ts` is imported by path so its own imports resolve from `apps/api/`, and a package manager that does not hoist — pnpm's default — installs the package exactly there. Against that project `pithy payments provision` still answered *"The payments capability is not installed. Run `pithy add payments`"* while the Worker beside it loaded the package without complaint. Resolution now looks along the project root's chain and then in each Worker's own `node_modules`; the root still wins where it has a copy, so every project that resolved before resolves to the identical file and the only change is that a refusal became an answer. It reaches the same two places `composedManifests` does for manifests (#507) and ranks them the other way round, deliberately: that function is asked about one Worker and can let it win, and a `pithy <capability>` command has no Worker in hand.

`pithy doctor`'s `capabilities:` section is left with the case no lookup can fix — a capability the project composes and has not installed anywhere — which is the one state `pithy add <capability>` is for, and which nothing else in the report notices: a capability with no manifest contributes no binding to check and no config option to read, so it reads as health until the next command refuses.
