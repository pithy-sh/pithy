Keep the server data layer out of a response schema.

A response schema is a module a browser imports. That is the whole reason §HTTP makes an admin response a Zod object rather than an interface: the client of an admin route is a management client reading a customer's Worker across a trust boundary, and it has to validate what comes back. `#418` added one line to `packages/support/src/http/responses.ts` — `import { SUPPORT_BILLING_SCOPE } from "../link/sender"` — and brought the sender's whole import list with it: `@pithy-sh/auth`'s Kysely builder, `@pithy-sh/payments`' table map, D1. `pithy-sh/dashboard`'s client program stopped compiling on `Cannot find name 'D1Database'` in a file it had never heard of.

**`SUPPORT_BILLING_SCOPE` now lives in `@pithy-sh/support/src/data/billingScope.ts`**, which imports nothing. The argument for declaring it once has not changed — the value the `WHERE` clause filters on and the value a console is told must be the same value — only where "once" is. `link/sender.ts` and `http/responses.ts` both import it and neither reaches the other.

**`CarriesNoValue` now lives in `@pithy-sh/secrets/src/valueBearing.ts`**, for the same reason found by the same sweep. `http/responses.ts` imported it from `admin/status.ts`, a Kysely reader, and a type-only import is still an edge the compiler follows: the D1 layer was in the browser program's file set, one bare Workers global away from the error support actually shipped.

**`@pithy-sh/auth/src/data/tables.ts` imports `D1Database` by name.** It named it off the global scope, which compiles only for a consumer that has already loaded `@cloudflare/workers-types` — and a browser program has not. This is what turned the import above from dead weight into a red build.

**The rule is now stated and held: a module a browser may import reaches no module that needs the Workers runtime.** `tooling/browser-scopes` gains a fourth program, compiling every capability's response schemas under the DOM lib with `types: []`, and a test that derives its expectation from the tree — every `packages/*/src/http/responses.ts`, so a capability landing tomorrow is covered by the commit that adds it. Beside it, an answer to the half `tsc` cannot give: a reached module that spells its Workers types *correctly* compiles everywhere and is server code all the same. `@pithy-sh/secrets` was failing that half while compiling green.

**That second half was a walk over the import graph, and three spellings walked past it in two rounds (Jim, 2026-08-21).** The walk found import specifiers with a regex over source text, and the argument for it read: *"the split is by what a program can refuse. `tsc` under `types: []` owns everything that fails in a browser's ambient environment; the walk owns everything a program cannot refuse, cannot read as a fault, or never got to look at."* **The split is still right. The walk was the wrong thing to put on its far side.** It missed `../link/sender.js`, which Bundler resolution follows to the `.ts` beside it. It missed `/// <reference types="@cloudflare/workers-types" />`, which the pattern never matched and which `tsc` honours whatever `types: []` says. It missed a comment inside a multi-line import list, because the pattern was `[^;]*?` and one semicolon anywhere in a statement stops it matching at all. Each of the three, planted, re-attached the whole #419 chain with `tsc -p tsconfig.responses.json` at exit 0 and the suite green. It failed the other way too: pointed at every module in `packages/`, it threw on 53 of 1,912 — 30 of them on an `import` statement that lives inside a scaffold **template literal**, and 23 on `.json` imports that `resolveJsonModule` makes real compiler-followed edges.

Three is not bad luck. It is the instrument. **A regex over source text is a second, hand-written model of TypeScript's grammar and of its module resolution, kept beside the real one, and the only thing it can ever be is behind.** So the walk is gone and the compiler answers: `tsc --listFiles` reports which files a program actually included, and every spelling above is one entry in that list — a named import, a subpath, a `.js` re-export three modules down, and a reference directive, whose *being honoured* and *appearing in the list* are the same event. A directive inside a template literal appears nowhere, because the compiler does not read emitted text. There is no fourth spelling to find, because nothing is spelled: the question asked is not what the text looks like but what the compiler opened.

The assertion is an allowlist of the packages a browser build may have — `zod`, and nothing else has ever been reached from those eight modules. A blocklist naming `@cloudflare/workers-types` would be the count-of-spellings mistake one level up, with `kysely-d1` and `wrangler` the next two entries somebody is behind on. One thing was given up: the walk printed a trail, and a file list prints none. What replaces it is one program per response module, so a failure names the capability, and `typecheck`'s own diagnostics name the file and the line for anything a browser's environment can refuse. #419's report was `packages/auth/src/data/tables.ts(35,34): error TS2552`, with no trail, and that was enough.

**And the gate never re-ran when its subject changed.** `@pithy-sh/browser-scopes`'s `test`, `test:node` and `typecheck` hashes were invariant to every file under `packages/` — its subject is every capability, its turbo inputs were its own package. Reproduced with the cache warm: with the #419 chain planted back, `turbo run test --filter=@pithy-sh/browser-scopes` printed `Cached: 1 cached` and `16ms >>> FULL TURBO`, replaying a `20 passed` from before the planted file existed. Forced, the same tree fails. `turbo.jsonc` names `$TURBO_ROOT$/packages/**` now — the whole tree rather than the files the programs open, because the coverage assertion is a directory walk whose answer changes when a file *appears*, and a file nothing yet imports is a file no compile opens. `turboInputs.test.ts` stands over the declaration: the expected set is derived from `.github/scripts/crossPackageReads.ts` and from `git ls-files`, the declaration is asked of `turbo --dry=json` rather than parsed, and `turbo.jsonc` is itself in the key so the way to silence the guard is not to edit the file it guards.

The same question, asked of this package's other two programs, answers `#430` with no machinery at all: `tsconfig.client.json` pulls in `@cloudflare/workers-types`, `hono`, `kysely` and `kysely-d1` today, because four `src/http/scopes.ts` modules and two `src/http/schemas.ts` modules reach the data layer through type-only edges. That is a change to `AdminRoute`'s shape in `@pithy-sh/core`, not a constant in the wrong module, and the gate says so where somebody would otherwise assume it covered them.

**One thing this deliberately does not change: `@pithy-sh/auth`'s manifest.** `data/tables.ts` now imports `D1Database` by name, and `@cloudflare/workers-types` is a devDependency there. That is `#431`, and it is not auth's alone — fifteen packages name the types package in shipped source and `@pithy-sh/core` is the only one that declares it as a dependency. Promoting this one would leave the ledger less legible than it is now: one package correct because a branch happened to touch it, thirteen wrong, and no gate. Nor does this branch create the need. `tables.ts` named `D1Database` off the global scope before it, which requires the same package present and merely fails with a worse message; the named import narrows the failure rather than inventing the dependency. `#431` moves all fourteen behind one gate, which is the shape that holds.
