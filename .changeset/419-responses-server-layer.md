Keep the server data layer out of a response schema.

A response schema is a module a browser imports. That is the whole reason §HTTP makes an admin response a Zod object rather than an interface: the client of an admin route is a management client reading a customer's Worker across a trust boundary, and it has to validate what comes back. `#418` added one line to `packages/support/src/http/responses.ts` — `import { SUPPORT_BILLING_SCOPE } from "../link/sender"` — and brought the sender's whole import list with it: `@pithy-sh/auth`'s Kysely builder, `@pithy-sh/payments`' table map, D1. `pithy-sh/dashboard`'s client program stopped compiling on `Cannot find name 'D1Database'` in a file it had never heard of.

**`SUPPORT_BILLING_SCOPE` now lives in `@pithy-sh/support/src/data/billingScope.ts`**, which imports nothing. The argument for declaring it once has not changed — the value the `WHERE` clause filters on and the value a console is told must be the same value — only where "once" is. `link/sender.ts` and `http/responses.ts` both import it and neither reaches the other.

**`CarriesNoValue` now lives in `@pithy-sh/secrets/src/valueBearing.ts`**, for the same reason found by the same sweep. `http/responses.ts` imported it from `admin/status.ts`, a Kysely reader, and a type-only import is still an edge the compiler follows: the D1 layer was in the browser program's file set, one bare Workers global away from the error support actually shipped.

**`@pithy-sh/auth/src/data/tables.ts` imports `D1Database` by name.** It named it off the global scope, which compiles only for a consumer that has already loaded `@cloudflare/workers-types` — and a browser program has not. This is what turned the import above from dead weight into a red build.

**The rule is now stated and held: a module a browser may import reaches no module that needs the Workers runtime.** `tooling/browser-scopes` gains a fourth program, compiling every capability's response schemas under the DOM lib with `types: []`, and a test that derives its expectation from the tree — every `packages/*/src/http/responses.ts`, so a capability landing tomorrow is covered by the commit that adds it. Beside it a walk over the import graph answers the half `tsc` cannot: a reached module that spells its Workers types *correctly* compiles everywhere and is server code all the same. `@pithy-sh/secrets` was failing that half while compiling green. The walk is proven against `link/sender.ts`, which it must catch.

**The rule is one invariant, and it was first written as a count of spellings.** "In either spelling — `tsc` owns the bare one, the walk owns the explicit one" was true of both spellings and wrong about the number. There is a third: `/// <reference types="@cloudflare/workers-types" />` defeats both halves at once, because the specifier regex matches statements and **`tsc` honours a reference directive whatever `types: []` says**. A module carrying that line with a bare `D1Database` under it compiled clean in the DOM-only program and drew no line from the walk. So the split is now by what a program can *refuse*: `tsc` under `types: []` owns everything that fails in a browser's ambient environment, and the walk owns everything a program cannot refuse, cannot read as a fault, or never got to look at. A directive is caught whatever types it names, because the fault is the injection and not the package.

**And the walk no longer discards an edge it cannot follow.** `resolveSpecifier` tried two candidates and dropped anything else in silence — including `../link/sender.js`, which TypeScript's Bundler resolution follows to the `.ts` beside it. One re-export in that spelling re-attached the whole #419 chain with both halves of the gate green. The `.js` family and `.tsx` now resolve; more to the point, a specifier naming something *inside this repository* that resolves to nothing throws, as does a module the walk cannot read. `zod` and `hono` still resolve to nothing on purpose, but that is now a case the walk decides rather than a hole it falls into. `reach.test.ts` holds each shape on fixtures, because two of the three have no producer in `packages/` today and a real-tree assertion about either would pass on an empty set forever.

The same walk finds four `src/http/scopes.ts` modules and two `src/http/schemas.ts` modules reaching the data layer through type-only edges. Those are `#430` — a change to `AdminRoute`'s shape in `@pithy-sh/core`, not a constant in the wrong module — and the gate says so where somebody would otherwise assume it covered them.

**One thing this deliberately does not change: `@pithy-sh/auth`'s manifest.** `data/tables.ts` now imports `D1Database` by name, and `@cloudflare/workers-types` is a devDependency there. That is `#431`, and it is not auth's alone — fifteen packages name the types package in shipped source and `@pithy-sh/core` is the only one that declares it as a dependency. Promoting this one would leave the ledger less legible than it is now: one package correct because a branch happened to touch it, thirteen wrong, and no gate. Nor does this branch create the need. `tables.ts` named `D1Database` off the global scope before it, which requires the same package present and merely fails with a worse message; the named import narrows the failure rather than inventing the dependency. `#431` moves all fourteen behind one gate, which is the shape that holds.
