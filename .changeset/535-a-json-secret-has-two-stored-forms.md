A `json` secret has two stored forms, `pithy turnstile provision` wrote one of them into the other's destination, and a value its own registry refuses is now refused at the write.

`turnstile provision` serialized the widget secret once and handed the same string to both destinations. One of them wanted it. The dev secrets file did not: it states a `json` secret's **own structure**, so what landed there was a JSON string containing JSON — and `TurnstileSecrets` is a `z.strictObject`, which refuses a string at the root. The writer exited 0 and printed `Test secret wired for dev and staging.`; the refusal arrived at the next `pithy doctor`, as *Secret 'turnstile-secret-keys' … failed validation at version '1'*, on a day unconnected to the run that caused it.

**The fix is not "drop a `JSON.stringify`", and reading it that way would break the other two writes.** The two stores have opposite conventions, and both are correct for what reads them. A D1 row and a Secrets Store entry hold the **canonical string**: `validateSecretValue` produces it on the way in, `parseValue` does `JSON.parse` and *then* `schema.safeParse` on the way out. The dev secrets file holds the **structure**: `storedVersion` hands the value straight to `schema.safeParse` with no parse first, because that file is hand-edited and an adopter should write real JSON rather than an escaped string inside a string. `storedSecretValue` is the one conversion between them. So the secret now crosses the provisioning seam as a `TurnstileSecrets` object and each destination encodes for itself — which leaves no encoding for a writer to guess at, and is why the change is in the seam rather than at three call sites.

**Only dev was ever affected.** Staging and production hold the canonical string, which is exactly what their store takes and what the middleware reads back; the original report could not check the runtime read path and assumed the worst, and the worst was not the case. Nothing in a deployed environment needs repairing on account of this.

**If a managed secret was deleted anyway, a re-provision will not put it back — and it will say `Done.`** `ensureProductionWidget` reuses the production widget by name, Cloudflare never returns an existing widget's secret, so `productionSecretWritten` is false and the production write is skipped. The run prints the line about widgets that already existed, and that line is the whole of the warning. Per environment: **dev** and **staging** come back from `pithy turnstile provision` alone, because both are wired with Cloudflare's published test pair and can be recomposed from nothing (dev's entry is `replace`d, then seeded by the next `pithy dev`). **Production** cannot be, and has two ways back: copy the widget's secret key from the Turnstile dashboard and pipe `{"visible":{"key":"…"}}` — the modes your config enables — into `pithy secrets create turnstile-secret-keys --env prod`, which keeps the sitekey and needs no redeploy; or run `pithy turnstile deprovision` then `pithy turnstile provision`, which recreates the widget with a **new sitekey** and therefore needs the front-end rebuilt with it.

**And a value its own registry refuses now fails at the write, on both forms.** `initialDevSecret` is the composer every dev-file writer goes through and it holds the registry entry, so it runs the check `storedVersion` would have run later — the same schema, at the moment there is still something to fix. `CloudflareTurnstileProvisioner.writeManagedSecret` goes through `validateSecretValue`, the CLI-side validator `pithy secrets create` has always used and this writer alone skipped; the manager Workflow cannot be the validator, because a brand-new secret's registry entry is bundled into no deployed manager yet. Had either existed, this would have been a failed command the first time `turnstile provision` ran anywhere.

The convention itself is written down now, in `dev/devSecretsFile.ts` beside the rule it belongs to, and pinned by a test that states both forms together and asserts each destination refuses the other's. Three write sites shipped this because the two halves were true in separate files and nothing joined them.

The tests assert the stored value **as stored**. The coverage this replaces compared `writeDev`'s argument against `JSON.stringify({ visible: … })` — content, not encoding — so it passed over a value serialized twice and would have passed over one serialized once. A `JSON.parse` in an assertion is the test doing the work the reader will not do.
