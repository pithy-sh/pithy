One namer for one bucket: `MEDIA_BUCKET` and `STORAGE_BUCKET` are composed once.

#513 gave `BindingSpec` a `resource` field — the `<thing>` segment where it is not the kebabbed binding name — and pointed every writer at it, and left these two out because they are the `resource` half without the `scope` half. So `pithy add` and `pithy provision` went on composing `<project>-<env>-media-bucket` from the binding name while `mediaBucketName` composed `<project>-<env>-media`. Two names for one bucket, which is exactly the property #513 exists to remove. `storage` had it identically.

**Both buckets were real, and the objects are in the one the capability names.** `pithy provision --env <env>` created `<project>-<env>-media-bucket` and wrote it into the stanza, so `env.MEDIA_BUCKET` opened it; `pithy media provision` created `<project>-<env>-media` and wrote its name into `media-r2-credentials`, which is the bucket every **presigned** URL addresses. Uploads never pass through the Worker, so they landed in the capability's bucket while a server-side read through the binding in the **app** Worker looked in the other one and found nothing — and `pithy media deprovision --storage` deleted the one holding the objects. The enrichment Worker is the exception that shows the shape: `resolveMediaConfig` binds its `MEDIA_BUCKET` to `<project>-<env>-media` directly, so `workflows/worker.ts`'s `env.MEDIA_BUCKET.get` was reading the right bucket all along. Converging the two points every binding at the bucket the uploads were already going to.

The manifests state it now — `"resource": "media"` and `"resource": "storage"` — so `pithy add` proposes that name and `pithy provision` creates and binds it. Each capability's namer already composed the same string and still does, through its own `resourceNames(project).env(env).r2(…)` call; the manifest line and the namer are two statements of one fact, held to each other by `ci/bindingResourceNames.test.ts`, which compares every provisionable binding in every shipped manifest against the function that names it at a four-character project name and at the longest one a config may declare. That gate carried an exemption row for each of these. Both are deleted, and it now has none.

**The binding keeps `_BUCKET` and the resource drops `-bucket`, deliberately.** A binding is read in a Worker as `env.MEDIA_BUCKET`, and the suffix is what says which kind of thing it is at the point of use. A resource name already carries its kind, because `r2` is the namespace it was composed for — so the suffix repeats it, and `docs/NAMING.md` has advertised the short form to adopters all along. Renaming the *binding* instead was considered and rejected under #513: `SUPPORT_BUCKET` appears as a key in an adopter's `declinedBindings`, which a rename would silently un-decline.

**Rollout, for a project that already has both buckets.** Not a hazard, but worth doing in order. `@pithy-sh/storage`'s sweep Workflow deletes on a cron, and it is already guarded twice over: candidates are filtered by `isDerivedObjectKey`, a prefix test on keys the capability minted itself — its docstring says the sweep uses it "to leave a co-tenant's objects alone" — and anything carrying a `pithy_storage_objects` row in a quota-counted status is skipped as claimed. So an adopter's own objects and any other capability's are untouched by construction. The narrow case the rename opens is storage's *own* derived objects sitting in the abandoned bucket, whose rows were written under the other name: those read as unclaimed. `StorageSweepParams.dryRun` exists for exactly this — run one dry sweep after the rename and before the first live one, and check what it would have deleted. There are no adopters on this path today, so the exposure is theoretical; recorded so the order is deliberate rather than lucky.

**Media has a second one, and it is the sharper half: objects the rename turns into permanent orphans.** Media's delete goes through `env.MEDIA_BUCKET`, which before this change opened `<project>-<env>-media-bucket` — the empty bucket. So an **R2-backed** media delete removed the `pithy_media_assets` row and was a no-op against the object, which was sitting in `<project>-<env>-media` all along, put there by a presigned upload. Only that branch: `media/src/storage/storage.ts` returns early for `cf-images` and `cf-stream`, which delete through their own APIs and always worked. Converging the binding fixes deletes from here on and does nothing for those: the row that named them is gone, so nothing in `media` will ever reach them again, and unlike `storage` there is no sweep to find them. They are billable bytes nobody can enumerate through the kit.

Any project that deleted an R2-backed media record before this release should list `<project>-<env>-media` over R2's S3 endpoint and reconcile it against `pithy_media_assets` before the rename, while the row set is still the one those objects were written under — a key with no row is a deleted record's object, and deleting it is safe. After the rename the same reconciliation still works; it just no longer has a moment where the two halves were written by the same version. `pithy media deprovision --storage` deleted the bucket holding the objects, which is the other half of this and is fixed by the same convergence.
