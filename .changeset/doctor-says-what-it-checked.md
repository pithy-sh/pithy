`pithy doctor` reports a capability it cannot reach, and stops calling Cloudflare reachable for products it never asked about.

Two follow-ons from the `pithy-sh/dashboard` bring-up on cli 0.2.2, both in the command an adopter runs *because* something is wrong.

**A capability the project composes that the CLI cannot resolve is now a `capabilities:` section in `Project health`.** A Worker's `pithy.config.ts` is imported by path, so its own imports resolve from `apps/<name>/`; every `pithy <capability> …` command resolves the same package from the **project root**. Those are two questions, and a project can pass the first and fail the second — install a capability under `apps/api/node_modules` alone, which is what "capabilities are per Worker" invites and what a package manager that does not hoist produces on its own, and the composition is perfect while every command that reaches into it refuses. Nothing said so: the refusal arrived one command at a time, in the sentence #533 was reported about, and the report the adopter turned to next was green. The section names the package, names where it *is* — `installed under apps/api/node_modules` — and names the one edit, which is the root `package.json` and never `pithy add`. It fails the exit, on the standard `manifests:` is held to: the fault is established from this project's own files, and a capability nothing can reach is also a capability contributing no manifest to the root scan and no drift to any Worker's checks. It compares packages and never modules, and only capabilities the catalog names, so a capability you wrote yourself is never reported as a missing `@pithy-sh/` package.

**The `Cloudflare:` line says what it checked.** It read `reachable (token active)`, and a bring-up took that as a green light on a token that could not reach Turnstile at all — learning the truth from `pithy turnstile provision`, after the account, the token and the config had each been ruled out in turn. The probe is two calls, verify the token and list the account's permission groups, and both are Account → API Tokens; Turnstile, D1, KV, R2, Vectorize, Workers AI, Email and Workers are never touched. The line is now `token active; checked: API tokens — no other product was reached`.

It was narrowed rather than widened, deliberately. The per-product probe available is a *read* — Turnstile's lists widgets — so a token holding Turnstile Read and not Edit would pass every one and still be refused by `provision`, under a line that had just said the product was checked: the same overclaim one level down, and a worse one for looking checked. The set is not derivable either, since `@pithy-sh/turnstile` declares no bindings at all — it is provisioned over REST and consumed as a secret — so the one product this was reported about is exactly the one a binding-derived list omits. A grant a command actually needs is a capability's own account-tier settings check, which knows what the grant has to *do* and runs against the credentials this line has already resolved.
