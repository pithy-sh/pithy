A refused social sign-in no longer says whether the account exists. Better Auth redirects to the adopter's `errorCallbackURL` with a code that answers the question directly — `account_not_linked` is returned only when a user row matched the provider-resolved address, `signup_disabled` only when none did — so pressing a provider button and reading the `Location` header enumerated accounts with no page load, needing one GitHub account and none on the target. It worked against `allowSignUp: false`, which is the configuration the kit's own guidance recommends, so the projects that followed the advice were the exposed ones. Both now leave the Worker as one code, `provider_sign_in_refused`, collapsed in `handleBetterAuth` where the capability hands the response back — composing `auth` is the whole of what an adopter does to get it, and an adopter's own middleware could only have collapsed the code and lost the reason with it. The reason survives server-side instead: these refusals reach `pithy_audit_events` as `auth/signin outcome=denied` with the true code, which no 302 ever had, because `DENIED_STATUSES` reads a status and a JSON body and a 302 is also what a *completed* sign-in answers with.

**Two more codes were on the same oracle, and the issue had cleared one of them.** `EMAIL_NOT_VERIFIED` describes the provider's state, but the kit throws it from `user.create.before` and a user is only ever created when no row matched — so with sign-up permitted, which is the default, the pair is `account_not_linked` against `EMAIL_NOT_VERIFIED` and it is the same oracle under another name, carrying a whole sentence of `error_description` besides. `unable_to_create_user` sits on the same branch. So the fix is a roster with a written verdict per code rather than two strings: the question each code answers is not whether its sentence is sensitive but whether the Worker could have produced it without looking in its own user table. Thirty codes were ruled safe and say why — the request's own state, the provider's own answer, the adopter's config, or the link flow, where the caller is signed in as the account being discussed. A completeness gate reads Better Auth's own error tables and the kit's own `APIError` sites and fails on any code with no verdict, so a dependency bump cannot reopen this quietly; it found three codes missing from the first draft of the roster.

**And the screen was narrating it.** The scaffolded sign-in template rendered "No account for this GitHub." on the code that meant exactly that, and the Spanish catalog said `No hay ninguna cuenta para este {provider}.` — a neutral header is worth nothing on a page that reads the answer aloud. The refusal copy now says what is true of both cases in both languages, and the remedy is unchanged because it was always the same one. The acceptance proof is an end-to-end one: a real auth capability over real D1, a real OAuth state, a refused callback driven twice — once with a seeded matching user, once without — and the two full responses diffed. Byte-identical, across both sign-up policies.

**Two ways round the collapse, both closed here.** The `Location` it reads is built from `errorCallbackURL`, which is the caller's own input, and the first version read it as though Better Auth had written all of it. Neither half held. It need not be absolute — `origin-check.mjs` passes `allowRelativePaths: true`, `matchesOriginPattern` admits `/path?query`, `oauth2/state.mjs` stores the value as a bare optional string and `redirectOnError` concatenates it raw — so `{"errorCallbackURL":"/sign-in"}` answered a relative header, `new URL()` threw on it, and the whole collapse returned early: the true code went to the browser and nothing reached the audit trail either. And `error` need not be the only one, because `redirectOnError` *appends*: an error URL ending `?error=access_denied` answered `?error=access_denied&error=account_not_linked`, and reading the first value let the caller pick which code the roster was shown. A relative target is now resolved against the request the way a browser resolves it and goes back relative; every `error` value is put to the roster rather than the first, and one collapsing code anywhere in the list collapses the lot to a single neutral parameter. Both are driven end to end, against real D1 and a real OAuth state, beside the original shape.

**The completeness gate said more than it did.** It claimed to read "the kit's own `APIError` sites" while reading one file, so an `APIError` thrown from a hook in any other file reached the redirect with no verdict and a green build; and it read none of `better-auth`'s own `APIError` sites, which arrive the same way — `callback.mjs:239` re-emits anything thrown inside `handleOAuthUserInfo` as `?error=<code>&error_description=<message>`. Both scans now cover the class they name: every non-test source in this package, and the dependency's own sites on the callback's path. That found nine codes with no verdict, one of which — `validation_context_missing` — is raised only inside `createUser`, which is the no-row side, so it collapses. Re-reading `link-account.mjs` for those verdicts also corrected one already written: `INVALID_PROFILE_FIELD` was cleared as proof of account ownership on the grounds that its `updateUser` sits inside `if (linkedAccount)`. It does not. It sits in the `overrideUserInfo` write that runs after either sub-branch of `if (dbUser)` — a matched row, nothing more, and the other side of that branch *sanitizes* the same two fields instead of refusing them. A hostile provider display name therefore answered one thing for an address with a row and another for an address without. It collapses.

**A third shape got past, and the seam moved.** `errorCallbackURL: http://localhost/sign-in#x` answered `…/sign-in#x?error=account_not_linked` for an address with an account and `…?error=signup_disabled` for one without — the whole oracle back, for one character, with no audit row behind it. The cause is that `redirectOnError` is raw string concatenation — `` `${baseURL}${baseURL.includes("?") ? "&" : "?"}${params}` `` — performed on a value the caller supplied, and it never parses; the appended code landed inside the fragment, and a collapse reading `searchParams` correctly found no `error` there. `http://localhost/sign-in#` does it too, whose `URL.hash` reads as empty before the append. **That is a diagnosis rather than a fourth entry for the table**: every input shape where the dependency's concatenation and our parsing disagree is another bypass, and patching the parser a third time only finds the fourth shape later, from a report. So `errorCallbackURL` is now guarded on the way **in**, before Better Auth stores it, and the invariant is that by the time `redirectOnError` concatenates, `errorURL` is a URL the kit produced: no fragment, no `error` or `error_description` already on it, and a `?` in it exactly when it carries a query — so appending `?k=v` or `&k=v` yields one readable query either way. Anything that cannot be normalized to that is refused at the door with a `400` naming the field, never silently rewritten into a destination the adopter did not ask for; what survives is canonicalization, and the caller's intent with it — a root-relative input stays root-relative, an absolute one stays absolute on its own origin.

**The output collapse stays, as the second line rather than the only one.** Two guards, one at each end: the input guard decides what the dependency is handed, and the collapse still checks what it answered against the roster. Keeping one would be a choice between two kinds of guessing, and an input guard that depends on out-guessing a dependency's string handling is the thing this round exists to stop relying on — so the guess is made once, about a value the kit then owns, and checked again at the other end. **Adopter-visible:** a fragment in `errorCallbackURL` and an `error` parameter already on it are now refused where they were accepted; `//host/path`, a bare-relative `sign-in?x` and an empty string are refused at the door as `400 validation/invalid_input` naming the field, where Better Auth's own origin check previously answered `403 INVALID_ERROR_CALLBACK_URL` — the same refusal, saying which property broke instead of reporting an origin that was never the problem. Round 2's own open question is answered end to end with it: `matchesOriginPattern` skips its relative branch for a bare-relative path because it does not start with `/`, then rules on `pattern === getOrigin(url)` with `getOrigin` returning null — the right refusal reached by an origin check with no origin to check.

**And the guard was reading the wrong bytes, so the door had a second entrance.** Guarding the value was right; deciding *which requests to look inside* was done twice over with a cheap test standing in for the parse it was supposed to precede, and both stand-ins were wrong. The body text was searched for the literal `errorCallbackURL` before being parsed — but JSON permits `\uXXXX` escapes in keys, so `"\u0065rrorCallbackURL"` is the same field after `JSON.parse` and shares not one byte with it beforehand; the search said no, the request went through untouched, and `{"provider":"github","\u0065rrorCallbackURL":"http://localhost/sign-in#"}` restored round 3's oracle whole, `account_not_linked` for an address with an account and `signup_disabled` for one without, with no audit row behind either. And the `content-type` was tested for the literal `application/json` — which is two of the three branches better-call's `getBody` builds a keyed object in missed outright, form-encoded and multipart, and part of the third besides, since the `+json` structured-suffix family is JSON to the dependency's own regex. Those three answer `415` on `/sign-in/social` today, but on somebody else's allow-list: `better-auth/plugins/device-authorization` already ships a route that widens `allowedMediaTypes`, an adopter's plugin may widen any route, and composing adopter plugins is the point. A guard whose reach depends on that list is one config change from the bypass being live with nothing turning red.

So the prefilter is gone rather than fixed, and the dispatch is now `getBody`'s own — the same three branches, the same predicates, the same order, and the same `request.body` test in place of a list of verbs, which is what had been leaving `PATCH` and `DELETE` unguarded. The performance claim the prefilter rested on did not survive being checked: the body had already been cloned and read to a string one line above, which is the copy, so what it avoided was a `JSON.parse` of a string in hand, on a body better-call parses anyway microseconds later. There was nothing on the other side of the trade. **Adopter-visible:** an `errorCallbackURL` in a form-encoded, multipart or `+json` body is now normalized or refused exactly as it is in `application/json`, and a form body naming the field twice is judged on the last value — which is the one `getBody` leaves for Better Auth to act on, where `URLSearchParams.get` answers the first.

**The gate is the relation, not the two spellings.** Listing what was found today is the same mistake one level up, so `errorCallbackUrlReach.workers.test.ts` runs both programs over one corpus of request shapes and compares them case by case: the guard reads an `errorCallbackURL` out of a request **exactly when** `getBody` hands Better Auth one. The dependency's half is executed rather than modeled — a real Better Auth instance over real D1, through a plugin endpoint declaring `allowedMediaTypes: []` so the measurement is taken against the parser rather than the allow-list guarding it — and no corpus entry declares an expected answer, so adding a shape costs a line and no verdict. Entries neither side reads are as load-bearing as the rest: they are what catches the guard reaching *further* than the dependency and refusing a configuration Better Auth would never have seen the field in. A bump that teaches `getBody` a new media type or a new decoding turns it red naming the shape.

**The guard read bodies, and the value also arrives in a query string.** `guardErrorCallbackURL` opened `if (!request.body) return request`, and `better-auth/plugins`' own `oauthPopup()` takes the field off a `GET`: `oauth-popup/index.mjs:143` stores `errorURL: c.query.errorCallbackURL`, and better-call's router builds `c.query` for every request whether or not one carries a body. So the fragment walked in untouched on that route and round 3's oracle was restored whole. The kit composes no popup plugin, but `AuthConfig.plugins` is a documented seam and `assertAdditivePlugins` permits that id, so every adopter who added one inherited it — which is why the proof is an adopter's Worker rather than an argument: `oauthPopup()` is composed through the seam, the popup is started over real D1, and a fragment in the query is refused at the door with a `400` naming the field and no state minted, while a usable value in the same query still redirects to the provider. **Adopter-visible:** an `errorCallbackURL` in a query string is now normalized or refused exactly as one in a body, and a rebuilt value travels on a rebuilt URL with the adopter's other parameters in their original order. A *repeated* one is left alone, because the router folds repeats into an array and an array is not the string `errorURL` is stored from — refusing it would be the guard reaching past the dependency, which is the other half of the same defect.

**And the module claimed one dispatch while running two decoders.** It said its branches were `getBody`'s — "the same predicates, in the same order… Not a superset and not a subset — equal" — and the predicates did match. The decoders did not: `getBody`'s urlencoded branch is `await request.formData()`, which decodes by the content type's real essence, where this module read `new URLSearchParams(await request.clone().text())`, which decodes raw bytes as a query string. The gap between them is reachable, because the two programs answer "which encoding is this?" with different halves of the same header — better-call's branch predicates `includes()` the whole `content-type` and match urlencoded first, while `formData()` dispatches on the essence, the part before the first `;`. So `multipart/form-data; note=application/x-www-form-urlencoded; boundary=…` sent both into the urlencoded branch, where `formData()` found the field and `URLSearchParams` found nothing, and the guard handed the request on untouched. It is fixed by removing the choice rather than by matching predicates harder, which would be the same cheap-test mistake in a third place: `request.formData()` already handles both encodings, which is why the dependency effectively has one decoder, so this module has one too and the mismatch cannot exist by construction. What survives of the distinction is the one thing the dependency's two branches genuinely do differently after decoding — the urlencoded branch stringifies every entry, so a file part reaches Better Auth as `"[object File]"` where the multipart branch leaves a `File` — and that is mirrored off the same predicate in the same order. The rebuild keeps the media type it arrived under: a multipart body is re-encoded with a fresh boundary and every *other* parameter on the header kept, because those parameters are what decided which branch the request lands in and dropping them would quietly move it to the other one.

**The differential gate reaches as far as the guard does.** It still executes better-call rather than modeling it — that is what makes a bump visible — and it now measures both channels: the probe endpoint reports what the router left in `c.query` beside what `getBody` left in the body, and the straddle assertion is made per channel, because a corpus that straddled the boundary on bodies alone is exactly the corpus that stayed green while the query channel went unguarded end to end. Better Auth's own `403 INVALID_ERROR_CALLBACK_URL` is read as an answer rather than a broken instrument: its origin check refuses a string it found, which is proof one was handed over.

**And the sixth round needed no malformed input at all, so the answer is a bound rather than a sixth guard.** Five rounds each closed one transport for a hostile `errorCallbackURL` and the next attacker found another. This one does not touch the field. `better-auth/plugins`' own `oauthPopup()` registers an after hook on the OAuth callback, lifts `error` and `error_description` off the `Location` Better Auth just wrote, and replaces the whole response with a 200 HTML page that posts both to the opener — so with a perfectly well-formed error URL, nothing to normalize and nothing to parse, the redirect the collapse reads never leaves the Worker and `account_not_linked` against `signup_disabled` is legible again. Everything the kit itself ships is clean; the failure needs a composed plugin. Guarding a sixth channel would have been the same move a sixth time, and the channels are not enumerable anyway — a plugin may write any response it likes. So the guarantee is bounded to what the kit can actually hold: it covers the kit's own routes and any composed plugin that answers refusals through `Location`, and `auth()` now refuses a plugin that answers them anywhere else. **Adopter-visible:** `auth({ plugins: [oauthPopup()] })` is a `400` at config load naming the plugin and saying what composing it would put back, where it previously composed and was quietly uncovered.

**The rule is a reviewed list, and that is a finding rather than a shortcut.** The honest predicate — the hook *replaces* the response instead of amending its headers — is a fact about the body of a function, and a composed plugin hands `auth()` an id, some callable matchers and opaque handlers. The property that can be read off the object, *does an after matcher claim the callback path*, is sound in the direction that matters and far too wide to refuse on: measured against every plugin `better-auth` 1.7.1 exports, seven claim it — `anonymous`, `bearer`, `last-login-method`, `multi-session`, `one-time-token`, `oauth-proxy` and `oauth-popup` — because `matcher: () => true` is the ordinary idiom for a hook that only wants to read `set-cookie`, and six of the seven amend headers and nothing else. Refusing on it would have printed, six times out of seven, a reason that is not true of the plugin named, which is the defect this issue keeps being about one level up. So the gate is a roster with a written verdict per plugin, and its completeness is gated rather than asserted: the suite scans `better-auth`'s own shipped plugin sources for the real predicate, `context.returned =`, and fails on any plugin family with no verdict — a bump that teaches a new plugin that move turns red naming the directory. The measurement behind the prose is executed too, so a docblock claiming a reach it no longer has cannot stay green.

**What this does not cover, said here rather than left for a seventh round.** An adopter's own plugin can replace the callback's response exactly as `oauthPopup` does, and nothing detects it: the gate runs inside their Worker while the config loads, where the only thing in hand is the object, and the source scan reaches the dependency's plugins because their source is on disk for the kit's own suite to read. Every docblock asserting the collapse now states the bound instead of the whole — the kit's own routes, and any composed plugin that answers refusals through `Location`.
