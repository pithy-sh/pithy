A refused social sign-in no longer says whether the account exists. Better Auth redirects to the adopter's `errorCallbackURL` with a code that answers the question directly — `account_not_linked` is returned only when a user row matched the provider-resolved address, `signup_disabled` only when none did — so pressing a provider button and reading the `Location` header enumerated accounts with no page load, needing one GitHub account and none on the target. It worked against `allowSignUp: false`, which is the configuration the kit's own guidance recommends, so the projects that followed the advice were the exposed ones. Both now leave the Worker as one code, `provider_sign_in_refused`, collapsed in `handleBetterAuth` where the capability hands the response back — composing `auth` is the whole of what an adopter does to get it, and an adopter's own middleware could only have collapsed the code and lost the reason with it. The reason survives server-side instead: these refusals reach `pithy_audit_events` as `auth/signin outcome=denied` with the true code, which no 302 ever had, because `DENIED_STATUSES` reads a status and a JSON body and a 302 is also what a *completed* sign-in answers with.

**Two more codes were on the same oracle, and the issue had cleared one of them.** `EMAIL_NOT_VERIFIED` describes the provider's state, but the kit throws it from `user.create.before` and a user is only ever created when no row matched — so with sign-up permitted, which is the default, the pair is `account_not_linked` against `EMAIL_NOT_VERIFIED` and it is the same oracle under another name, carrying a whole sentence of `error_description` besides. `unable_to_create_user` sits on the same branch. So the fix is a roster with a written verdict per code rather than two strings: the question each code answers is not whether its sentence is sensitive but whether the Worker could have produced it without looking in its own user table. Thirty codes were ruled safe and say why — the request's own state, the provider's own answer, the adopter's config, or the link flow, where the caller is signed in as the account being discussed. A completeness gate reads Better Auth's own error tables and the kit's own `APIError` sites and fails on any code with no verdict, so a dependency bump cannot reopen this quietly; it found three codes missing from the first draft of the roster.

**And the screen was narrating it.** The scaffolded sign-in template rendered "No account for this GitHub." on the code that meant exactly that, and the Spanish catalog said `No hay ninguna cuenta para este {provider}.` — a neutral header is worth nothing on a page that reads the answer aloud. The refusal copy now says what is true of both cases in both languages, and the remedy is unchanged because it was always the same one. The acceptance proof is an end-to-end one: a real auth capability over real D1, a real OAuth state, a refused callback driven twice — once with a seeded matching user, once without — and the two full responses diffed. Byte-identical, across both sign-up policies.

**Two ways round the collapse, both closed here.** The `Location` it reads is built from `errorCallbackURL`, which is the caller's own input, and the first version read it as though Better Auth had written all of it. Neither half held. It need not be absolute — `origin-check.mjs` passes `allowRelativePaths: true`, `matchesOriginPattern` admits `/path?query`, `oauth2/state.mjs` stores the value as a bare optional string and `redirectOnError` concatenates it raw — so `{"errorCallbackURL":"/sign-in"}` answered a relative header, `new URL()` threw on it, and the whole collapse returned early: the true code went to the browser and nothing reached the audit trail either. And `error` need not be the only one, because `redirectOnError` *appends*: an error URL ending `?error=access_denied` answered `?error=access_denied&error=account_not_linked`, and reading the first value let the caller pick which code the roster was shown. A relative target is now resolved against the request the way a browser resolves it and goes back relative; every `error` value is put to the roster rather than the first, and one collapsing code anywhere in the list collapses the lot to a single neutral parameter. Both are driven end to end, against real D1 and a real OAuth state, beside the original shape.

**The completeness gate said more than it did.** It claimed to read "the kit's own `APIError` sites" while reading one file, so an `APIError` thrown from a hook in any other file reached the redirect with no verdict and a green build; and it read none of `better-auth`'s own `APIError` sites, which arrive the same way — `callback.mjs:239` re-emits anything thrown inside `handleOAuthUserInfo` as `?error=<code>&error_description=<message>`. Both scans now cover the class they name: every non-test source in this package, and the dependency's own sites on the callback's path. That found nine codes with no verdict, one of which — `validation_context_missing` — is raised only inside `createUser`, which is the no-row side, so it collapses. Re-reading `link-account.mjs` for those verdicts also corrected one already written: `INVALID_PROFILE_FIELD` was cleared as proof of account ownership on the grounds that its `updateUser` sits inside `if (linkedAccount)`. It does not. It sits in the `overrideUserInfo` write that runs after either sub-branch of `if (dbUser)` — a matched row, nothing more, and the other side of that branch *sanitizes* the same two fields instead of refusing them. A hostile provider display name therefore answered one thing for an address with a row and another for an address without. It collapses.
