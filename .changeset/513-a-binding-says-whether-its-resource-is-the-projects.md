A binding says whether its resource belongs to the project or to the environment.

`BindingSpec` carried `type`, `name`, `optional`, `className`, `classModule`, `job`, `service` and `remote`, and no way to say that one resource serves the whole project. So `pithy add email` wrote three per-environment suppression databases — `<project>-dev-`, `<project>-staging-`, `<project>-prod-email-suppressions` — where `@pithy-sh/email` requires exactly one, "bound identically in every environment", named `<project>-global-email-suppressions`. `pithy email provision` created that one. The app Worker and the email Worker then read different suppression lists, and **an unsubscribe recorded on one was invisible to the other**.

`SECRETS` sits one line from `EMAIL_SUPPRESSIONS` in the same env and is genuinely per-environment, so the two cannot be told apart by convention. The distinction is declarable now: `scope: "environment" | "global"` and `resource` — the `<thing>` segment where it is not the binding name — on the manifest, refused on any kind that provisions no resource. `@pithy-sh/email` declares `EMAIL_SUPPRESSIONS` global; `@pithy-sh/support` declares `SUPPORT_BUCKET` global and its resource `support`, which is the name that command has always created.

One composer reads it. `pithy add`, `pithy provision`, and each capability's own provisioner compose the name through the same expression, so the resource has one name rather than two writers of it — and a whole-repo gate now holds every provisionable binding in every shipped manifest against the capability that names it, at a four-character project name and at the longest one a config may declare.

**Upgrading an existing project: copy the data across first, then run `pithy provision --env <env>`, once per declared environment.** That order is the whole of it, and the reverse loses data. The per-environment resource is the one that has been in use: `EMAIL_SUPPRESSIONS` and `SUPPORT_BUCKET` are both bound in the **app** Worker's env, so the unsubscribe callback wrote every suppression into the per-environment database and every attachment and raw message went into the per-environment bucket. The project-global one — the one `pithy email provision` and `pithy support provision` create — is the empty side of the split, and `pithy support deprovision --storage` has been deleting *that* one while the correspondence stayed on the account.

So the loss is at the repoint, not at a delete. An unsubscribed recipient starts receiving mail again the moment the app reads a database that never heard about them; a stored attachment becomes unreachable the moment the binding names a different bucket. Nothing is deleted, and nothing is put back by re-running anything.

There is no safe automatic path and Pithy does not invent one: a cross-resource copy under your credentials is not something a diagnostic does on your behalf, and for R2 it is an S3-protocol job a Cloudflare API token cannot reach at all. `wrangler d1 export` each old database and `wrangler d1 execute --file` the dump against `<project>-global-email-suppressions`; sync each old bucket into `<project>-global-support` over R2's S3 endpoint, with a key pair from **R2 → Manage API tokens**. Then provision. The old resources are left exactly where they are until you delete them yourself. The top-level `dev` stanza is unreachable by `provision`, which writes `env.<stanza>` and never `dev`, and keeps its old name; it is inert, because wrangler keys a local database on the binding when the entry carries no `database_id`. Nothing rewrites it, and nothing needs to.

`pithy doctor` grew the section that finds this: `shared:` names every stanza pointing at something other than the project's one resource, the correct name, the carry-over above, and the command that repoints it — and the second shape of the same fault, two stanzas that name the right database and carry two different `database_id`s. It is the only thing that will ever tell an already-scaffolded project it is split, because every other reader keys on the binding name alone, deliberately, so that a binding you repointed at your own database is never reported as a missing one. It is keyed on the capability's own namer rather than on the manifest field, so a newer CLI beside an older `@pithy-sh/email` still answers — **and under exactly that skew it says the run is not the whole remedy**, because `provision` composes the name from the older manifest and would write the per-environment one straight back. There it names the package to upgrade first. A command that cannot clear the finding it is printed under is not printed. The list of which bindings are project-global is the CLI's own rather than the manifests', for that same reason, and `cli/src/ci/globalBindings.test.ts` holds it to every manifest that ships — so a third capability declaring `scope: "global"` cannot be invisible to the one check built to find a split.

`pithy provision` also names any installed `pithy.manifest.json` it could not read — the `faults` half of the scan it had been discarding (#184). The bindings still come from the composed capability, so the resources are still created; what a broken manifest costs is the `scope` and the `resource` that decide what they are **called**, so a project-global database gets created per environment and the run reports success. It is in the plan printed before the confirmation, in the summary, and in `--json` as `manifestFaults`.

`MEDIA_BUCKET` and `STORAGE_BUCKET` had the same split without the `global` half — `<project>-<env>-media-bucket` against `<project>-<env>-media`. #519 closes both in this release, and the gate has no exemption rows left.
