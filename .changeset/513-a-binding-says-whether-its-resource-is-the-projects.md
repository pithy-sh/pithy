A binding says whether its resource belongs to the project or to the environment.

`BindingSpec` carried `type`, `name`, `optional`, `className`, `classModule`, `job`, `service` and `remote`, and no way to say that one resource serves the whole project. So `pithy add email` wrote three per-environment suppression databases — `<project>-dev-`, `<project>-staging-`, `<project>-prod-email-suppressions` — where `@pithy-sh/email` requires exactly one, "bound identically in every environment", named `<project>-global-email-suppressions`. `pithy email provision` created that one. The app Worker and the email Worker then read different suppression lists, and **an unsubscribe recorded on one was invisible to the other**.

`SECRETS` sits one line from `EMAIL_SUPPRESSIONS` in the same env and is genuinely per-environment, so the two cannot be told apart by convention. The distinction is declarable now: `scope: "environment" | "global"` and `resource` — the `<thing>` segment where it is not the binding name — on the manifest, refused on any kind that provisions no resource. `@pithy-sh/email` declares `EMAIL_SUPPRESSIONS` global; `@pithy-sh/support` declares `SUPPORT_BUCKET` global and its resource `support`, which is the name that command has always created.

One composer reads it. `pithy add`, `pithy provision`, and each capability's own provisioner compose the name through the same expression, so the resource has one name rather than two writers of it — and a whole-repo gate now holds every provisionable binding in every shipped manifest against the capability that names it, at a four-character project name and at the longest one a config may declare.

**Upgrading an existing project: copy the data across first, then run `pithy provision --env <env>`, once per declared environment.** That order is the whole of it, and the reverse loses data. The per-environment resource is the one that has been in use: `EMAIL_SUPPRESSIONS` and `SUPPORT_BUCKET` are both bound in the **app** Worker's env, so the unsubscribe callback wrote every suppression into the per-environment database and every attachment and raw message went into the per-environment bucket. The project-global one — the one `pithy email provision` and `pithy support provision` create — is the empty side of the split, and `pithy support deprovision --storage` has been deleting *that* one while the correspondence stayed on the account.

So the loss is at the repoint, not at a delete. An unsubscribed recipient starts receiving mail again the moment the app reads a database that never heard about them. The bucket is the same shape with one more address in it: `SUPPORT_BUCKET` is write-only — every read is a presigned URL signed against `support-r2-credentials` — so the repoint moves the writes and every attachment stored afterwards 404s, while what is already there stays readable until the secret moves and unreachable once it does. Nothing is deleted, and nothing is put back by re-running anything.

There is no safe automatic path and Pithy does not invent one: a cross-resource copy under your credentials is not something a diagnostic does on your behalf, and for R2 it is an S3-protocol job a Cloudflare API token cannot reach at all. The order is: make the destination if it is not there yet (`pithy email provision`, `pithy support provision` — doctor reads files and never reaches your account, so it cannot know whether either has run, and skipping this leaves you live on a resource `pithy provision` created empty seconds earlier); copy the data in; provision; and for `SUPPORT_BUCKET`, `pithy secrets update support-r2-credentials --env <env>` beside it. The old resources are left exactly where they are until you delete them yourself. The top-level `dev` stanza is unreachable by `provision`, which writes `env.<stanza>` and never `dev`, and keeps its old name; it is inert, because wrangler keys a local database on the binding when the entry carries no `database_id`. Nothing rewrites it, and nothing needs to.

**The D1 copy is not an export piped into an import, and the terminal no longer pretends it is.** `wrangler d1` defaults to **local**: run without `--remote` the export reads `.wrangler/state`, prints `Done!`, and exits 0, so the repoint on the next line goes in underneath an operator who believes production was copied. With `--remote` the pair still cannot work — the dump carries `pithy_migrations`, `pithy_migrations_owner`, `sqlite_sequence` and an explicit `id` per row, all of which the destination already holds because `pithy email provision` created and migrated it, so the execute aborts transactionally on the first `UNIQUE constraint failed` and copies nothing. What works is narrow: a `--remote --table pithy_email_suppressions --no-schema` export whose `id` column is dropped and whose statements carry an `ON CONFLICT(email) DO UPDATE … WHERE` clause, because both environments allocated ids from 1 and `email` is unique. That last step is a text edit rather than a command, so the report prints the URL of the section carrying the verified sequence — `pithy.sh/docs/cli/commands/doctor#carrying-the-data-across` — instead of a command it cannot stand behind, and a URL rather than a repository path because `docs/` is not in the published package. The clause is also what settles which row wins: one address suppressed in two environments is two rows that merge into one, and it keeps the earlier row unless one expires and the other does not, because a permanent suppression is never replaced by a temporary one. In practice that means the date — every suppression the kit itself writes is permanent, so two rows you actually find in two environments agree on the expiry test and the decision falls to `created_at`; the expiry rules are there for a `manual` block written through the control-plane route. "Do not email this person again" is not a fact to settle by whichever export ran first, which is what `INSERT OR IGNORE` would have done.

**Repointing `SUPPORT_BUCKET` without `support-r2-credentials` breaks every attachment read.** Attachments are written through `env.SUPPORT_BUCKET`, and every **presigned** URL is signed against the `bucket` field inside that secret — a second string the repoint does not touch. Move one without the other and writes land in `<project>-global-support` while signed reads keep addressing the per-environment bucket, so everything stored after the repoint 404s. Nothing in the kit writes it: `pithy support provision` writes no secret, and only `storage` and `media` have provisioners that write theirs. So the report prints the second command beside the first, per environment — and names `pithy secrets create` after them, since nothing in the kit writes this secret and `update` refuses one that is not there. `media` had the same shape and needs no such step — #519 converged `MEDIA_BUCKET` *onto* the name `media-r2-credentials` already carried.

**The divergent half has its own remedy now, because it is a different job.** Two stanzas that carry the right name and two different `database_id`s have nothing stale by name, so "export each old database, then execute it against `<project>-global-email-suppressions`" named one string as both source and destination — a database exporting into itself, and `wrangler d1 export` addresses a database by name or binding and never by id anyway. What is true there is that two resources are open, one survives, and `pithy provision` picks it by resolving the *name* on your account rather than by reading the ids — so the decision is yours, the ids in the report are what it is made from, and the losing resource's rows move first. The run lines are enumerated per environment from `ids[].at[].env`, which the entry carried all along while the remedy printed a `<env>` placeholder nobody could paste. And the copy is addressed differently: two databases answering to one name is exactly the state that name cannot resolve, so the branch sends you to a subsection that reaches each one through `-e <env>` and its binding, which is the only form that does.

`pithy doctor` grew the section that finds this: `shared:` names every stanza pointing at something other than the project's one resource, the correct name, the carry-over above, and the command that repoints it — and the second shape of the same fault, two stanzas that name the right database and carry two different `database_id`s. It is the only thing that will ever tell an already-scaffolded project it is split, because every other reader keys on the binding name alone, deliberately, so that a binding you repointed at your own database is never reported as a missing one. It is keyed on the capability's own namer rather than on the manifest field, so a newer CLI beside an older `@pithy-sh/email` still answers — **and under exactly that skew it says the run is not the whole remedy**, because `provision` composes the name from the older manifest and would write the per-environment one straight back. There it names the package to upgrade first. A command that cannot clear its finding on its own is never printed on its own: the step that makes it work is printed above it, every time. The list of which bindings are project-global is the CLI's own rather than the manifests', for that same reason, and `cli/src/ci/globalBindings.test.ts` holds it to every manifest that ships — so a third capability declaring `scope: "global"` cannot be invisible to the one check built to find a split.

`pithy provision` also names any installed `pithy.manifest.json` it could not read — the `faults` half of the scan it had been discarding (#184). The bindings still come from the composed capability, so the resources are still created; what a broken manifest costs is the `scope` and the `resource` that decide what they are **called**, so a project-global database gets created per environment and the run reports success. It is in the plan printed before the confirmation, in the summary, and in `--json` as `manifestFaults`.

`MEDIA_BUCKET` and `STORAGE_BUCKET` had the same split without the `global` half — `<project>-<env>-media-bucket` against `<project>-<env>-media`. #519 closes both in this release, and the gate has no exemption rows left.
